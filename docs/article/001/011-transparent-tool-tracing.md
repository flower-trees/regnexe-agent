# 工具执行过程透明可追踪：让企业知道 Agent 为什么这么做

企业使用 Agent，最怕的是“它给了一个答案，但没人知道它怎么来的”。

对于简单聊天，这可能还能接受。对于企业任务，尤其是涉及合同、财务、客户、代码和运维的任务，过程必须可追踪。

Regnexe 在工具调用层面提供清晰日志，让每次工具调用和结果都可见。

## 为什么工具追踪重要

Agent 的最终答案通常来自多个步骤。

例如商务出差助手可能先调用天气工具，再调用合同分析能力，最后调用行程规划能力。

如果只保存最终答案，业务人员无法判断：

- 天气数据是否正确
- 合同分析是否真的执行
- 行程规划是否使用了天气结果
- 哪个工具返回了异常
- 哪一步导致结果偏差

工具追踪就是为了回答这些问题。

## 清楚记录工具调用

Regnexe 的执行日志会记录工具调用：

```text
[TOOL Call   ] R1 get_weather {"city": "成都"}
[TOOL Result ] R1 get_weather -> 多云转阴，18~25 C，偶有小雨
```

它清楚展示：

- 调用了哪个工具
- 工具输入是什么
- 工具返回是什么

这对排查非常直接。

如果天气结果错误，问题可能出在天气工具；如果工具没被调用，问题可能出在 Planner。

## Skill 和 SubAgent 内部也可追踪

Regnexe 不只追踪顶层工具，也追踪 Skill 和 SubAgent 内部工具调用。

例如：

```text
[TOOL Call   ] R1 [skill:contract_analyzer] analyze_clause {"clause": "条款 5..."}
[TOOL Result ] R1 [skill:contract_analyzer] analyze_clause -> 风险等级：中
```

又例如：

```text
[TOOL Call   ] R1 [subagent:travel_planner] get_restaurants {"city": "成都"}
[TOOL Result ] R1 [subagent:travel_planner] get_restaurants -> 推荐商务餐厅：银石盘、酒店商务套餐
```

这说明复杂能力内部不是黑盒。

即使任务委托给 Skill 或 SubAgent，企业仍然可以知道它内部用了哪些工具。

## 支持审计和责任定位

工具执行追踪可以帮助企业判断责任边界。

如果最终答案错误，可以进一步分析：

- 是 Planner 选错能力
- 是工具参数错误
- 是工具返回错误
- 是结果综合阶段遗漏
- 是 Reflect 没有发现问题

这比“模型回答错了”更有工程价值。

企业可以针对具体环节优化，而不是盲目改提示词。

## 与 TaskStore 结合

工具调用记录如果只出现在控制台，价值有限。

结合 TaskStore 后，工具执行过程可以成为任务状态的一部分，用于：

- 历史回放
- 审计留痕
- 失败重试
- 客诉排查
- 任务质量分析

这让 Agent 执行过程从“日志”升级为“可管理数据”。

## 商业价值

第一，提高信任。

业务方可以看到 Agent 的答案来自哪些工具和数据。

第二，便于排错。

问题可以定位到具体工具调用，而不是泛泛归因给模型。

第三，支持审计。

涉及敏感业务时，工具调用和结果可以留痕。

第四，支持优化。

平台团队可以分析哪些工具常失败、哪些能力常被误选。

第五，提升可解释性。

Agent 的执行过程可以被业务人员理解，而不是只有开发者能看懂。

## 结语

企业 Agent 不应该只给答案，还应该能解释答案从哪里来。

Regnexe 通过清晰的 Tool Call 和 Tool Result 记录，让工具执行过程透明可追踪。

这就是 Regnexe 的第十一项核心商业价值：

**每次工具调用和结果都有明确日志，企业可以知道 Agent 为什么这么做、用了哪个能力、返回了什么。**
