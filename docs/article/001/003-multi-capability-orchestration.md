# Regnexe 的多能力协同编排：让 Agent 从单点问答走向业务流程自动化

企业需要的不是一个会回答问题的 Agent，而是一个能完成业务流程的 Agent。

单点问答解决的是“一个问题，一个答案”。但企业业务往往不是这样运行的。一个真实任务可能同时涉及数据查询、规则分析、文档处理、规划生成、结果汇总和风险判断。

例如，一个商务出差任务可能包含：

- 查询目的地天气
- 分析差旅报销条款
- 规划三天行程
- 推荐合适餐厅
- 根据天气给出穿衣和交通建议

如果 Agent 只能调用一个工具，它最多只能完成其中一部分。真正有商业价值的 Agent，必须能把多个能力组合起来，形成完整业务结果。

Regnexe 的多能力协同编排，正是为这种场景设计的。

## 单点工具调用的局限

很多 Agent 系统的第一步，是让模型学会调用工具。

这当然重要，但还远远不够。

因为企业任务经常有这些特点：

- 一个目标需要多个工具共同完成
- 工具之间存在先后依赖
- 某个工具的输出会成为另一个工具的输入
- 最终答案需要综合多个结果
- 不能因为最后一个工具输出很长，就忽略前面工具的结论

例如用户说：

> 我下周去成都出差，请查天气、分析差旅报销条款风险，并根据天气安排三天商务行程。

如果系统只返回最后一个行程规划结果，却漏掉天气建议和条款风险，那么任务并没有完成。

这就是单点工具调用的局限。

企业需要的是协同编排，而不是孤立调用。

## 多能力协同是什么

Regnexe 中，每个能力都可以被统一描述和调度：

- `get_weather`：查询天气
- `contract_analyzer`：分析合同或制度条款风险
- `travel_planner`：规划行程
- `code_workspace_agent`：搜索代码、读取文件、运行验证

这些能力可以是 Tool，也可以是 Skill 或 SubAgent。

当用户提出复杂目标时，Regnexe 的 Planner 会判断哪些能力需要参与，并给出执行计划。

例如：

```text
[Search Result ] R1 Found 4 capabilities: get_weather, analyze_clause, contract_analyzer, travel_planner
[Plan Result   ] R1 Selected: [get_weather, contract_analyzer, travel_planner] | Strategy: SYNTHESIZE
```

这里的关键不只是“选中了三个能力”，而是 `Strategy: SYNTHESIZE`。

它表示最终答案不能只取最后一个工具结果，而要综合多个能力的输出。

## 从任务目标到能力组合

多能力协同的第一步，是理解用户目标中包含几个子任务。

比如这个目标：

```text
我下周要去成都出差三天。
请帮我完成三件事：
1. 查询成都近期天气，并给出穿衣和出行建议；
2. 分析我们差旅报销条款中的风险；
3. 基于天气情况，规划三天商务出差行程。
```

Regnexe 会把它理解成三个不同任务：

```text
天气查询 → 条款风险分析 → 天气约束下的行程规划
```

对应能力可能是：

```text
get_weather        → 获取天气和穿衣建议
contract_analyzer  → 分析报销条款风险
travel_planner     → 结合天气规划商务行程
```

这不是固定流程，也不是手写 if/else。Planner 会根据 Marketplace 中的能力描述动态选择。

## 能力之间可以传递上下文

多能力协同不仅是“调用多个工具”，还包括能力之间的上下文传递。

例如，天气结果会影响行程规划：

```text
get_weather 输出：
成都：多云转阴，18~25 C，偶有小雨。
建议携带雨伞和薄外套，上午更适合安排户外活动。
```

Planner 可以让 `travel_planner` 使用这段天气信息：

```text
travel_planner input:
成都三天商务出差。
天气：多云转阴，18~25 C，偶有小雨。
上午更适合安排户外活动。
请规划工作安排和餐厅推荐。
```

这样生成的行程就不是孤立模板，而是受前一个能力结果约束的业务输出。

对企业来说，这一点非常关键。

因为真实流程里，前一步结果经常决定后一步策略。

## 结果策略：RETURN_LAST 与 SYNTHESIZE

多能力协同中，一个容易被忽略的问题是：最终结果应该怎么返回？

如果任务是：

> 查一下北京天气。

那么最后一个天气工具结果可能就是完整答案。这时可以使用 `RETURN_LAST`。

但如果任务是：

> 查天气、分析合同、规划行程。

最终答案必须包含多个能力的结果。这时就应该使用 `SYNTHESIZE`。

Regnexe 支持结果策略，让 Planner 根据用户语义决定最终答案方式：

```text
RETURN_LAST → 最后一个能力已经产出完整答案
SYNTHESIZE  → 需要综合多个能力结果
```

这解决了复杂任务中常见的问题：最后一个能力输出很长，模型就把前面能力结果忘掉。

在企业场景里，这不是小问题。

如果合同风险分析被遗漏，业务决策就可能出错；如果天气建议被遗漏，行程安排就可能不合理。

## 一个商务出差协同案例

下面是一个典型执行过程：

```text
[Plan Result   ] R1 Selected: [get_weather, contract_analyzer, travel_planner] | Strategy: SYNTHESIZE
[TOOL Call     ] R1 get_weather {"city": "成都"}
[TOOL Result   ] R1 get_weather -> 多云转阴，18~25 C，偶有小雨
[TOOL Call     ] R1 contract_analyzer {"input": "条款 2... 条款 5..."}
[TOOL Result   ] R1 contract_analyzer -> 报销条款将较多成本风险转移给员工
[TOOL Call     ] R1 travel_planner {"input": "结合天气数据规划三天商务行程"}
[TOOL Result   ] R1 travel_planner -> 第一天文化参访和会议，第二天商务区拜访，第三天收尾安排
[Execute Result] R1 SUCCESS | 天气建议 + 条款风险 + 商务行程
```

这个过程体现了三个层次的协同：

第一，能力选择协同。

Planner 同时选择天气、合同、行程三个能力。

第二，上下文协同。

天气能力的结果被用于行程规划。

第三，结果协同。

最终答案综合天气、条款风险和行程，而不是只返回最后一个行程。

## 多能力协同适合哪些业务场景

这种编排能力适合大量企业流程。

例如销售场景：

- 查询客户画像
- 分析历史沟通记录
- 生成跟进策略
- 输出拜访计划

例如法务场景：

- 抽取合同条款
- 分析风险等级
- 检查缺失条款
- 生成修改建议

例如研发场景：

- 搜索相关代码
- 读取关键文件
- 运行测试
- 总结变更风险

例如运营场景：

- 查询业务指标
- 识别异常波动
- 生成原因分析
- 输出行动建议

这些都不是单点问答，而是多能力协同。

## 商业价值：把 Agent 变成业务流程执行器

多能力协同编排的商业价值非常直接。

第一，它让 Agent 能处理更复杂的任务。

用户不需要把任务拆成多个问题逐个问，Agent 可以一次接收完整目标，然后自动拆解和执行。

第二，它减少人工流程拼接。

过去需要人手动查系统、复制结果、再交给另一个系统处理。现在 Agent 可以把多个能力串起来。

第三，它提升结果完整性。

`SYNTHESIZE` 策略确保多个能力结果都能进入最终答案，减少遗漏。

第四，它适合跨部门流程。

天气、合同、行程只是示例。真实企业中，销售、财务、法务、研发、运营都可以通过能力市场接入同一个协同框架。

第五，它为业务自动化提供统一入口。

用户只需要表达目标，不需要知道背后有多少工具、什么顺序、怎么传递结果。

## 结语

企业 Agent 的价值，不在于单个工具有多强，而在于能不能把多个能力组织成完整业务流程。

Regnexe 的多能力协同编排，让同一个任务可以组合 Tool、Skill、SubAgent，把查询、分析、规划、验证等动作串成一个完整结果。

这就是 Regnexe 的第三项核心商业价值：

**它让 Agent 从单点问答升级为业务流程自动化执行器，能够把多个企业能力组织起来，共同完成复杂任务。**
