# Harness Marketplace 剖析系列 - 之 OpenCode：从 `.opencode` 到 `opencode.json`，先看懂它的扩展体系

如果你已经看过 Claude Code、Codex 这类 AI Coding Harness，再打开 OpenCode，很容易产生一种错觉：

> 不就是又一个可以在终端里调用大模型、读写代码、执行 Bash、接 MCP 的 Coding Agent 吗？

但如果从 Harness 的工程视角去看，OpenCode 有一个非常鲜明的特点：

**它把大量扩展能力直接暴露成了目录、Markdown、JSON 配置以及 TypeScript / JavaScript 扩展接口。**

也就是说，OpenCode 不只是给你一个 Agent。

它实际上提供了一整套可以被用户重新组合的 Harness 扩展面：

```text
AGENTS.md
    ↓
Instructions

commands/
    ↓
User Workflow

skills/
    ↓
Agent Workflow

agents/
    ↓
Agent Definition

tools/
    ↓
Executable Capability

MCP
    ↓
External Capability

plugins/
    ↓
Runtime Extension

permission
    ↓
Runtime Policy
```

OpenCode 官方仓库将其定位为开源 Coding Agent，同时强调 Provider Agnostic、LSP，以及 Client/Server Architecture 等特点。

但这一篇我们暂时不讨论它的 Agent Loop，也不讨论 Plugin Hook 是怎么真正介入 Tool Execution 的。

我们先完成一件更基础的事：

> **建立 OpenCode Harness 的静态架构地图。**

也就是回答：

```text
OpenCode 的配置在哪里？

项目规则在哪里？

Agent 在哪里定义？

Skill 放在哪里？

Command 和 Skill 有什么区别？

Tool 怎么扩展？

Plugin 又是什么？

MCP 从哪里进入 Runtime？

Permission 位于什么位置？
```

只有先把这些入口摆正，后面才能继续讨论：

```text
Discovery
    ↓
Loading
    ↓
Registration
    ↓
Routing
    ↓
Execution
    ↓
Permission
    ↓
Runtime
```

---

# 一、先不要把 OpenCode 当成一个 CLI

从表面看，OpenCode 是一个 Coding Agent。

但如果把 UI、模型供应商这些东西暂时拿掉，只看它暴露出来的扩展结构，会得到一个更接近 Harness 的模型：

```text
                         OpenCode
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ↓                  ↓                  ↓
     Instruction        Agent Definition    Capability
          │                  │                  │
     AGENTS.md             agents/        ┌─────┼─────┐
     instructions                         ↓     ↓     ↓
                                      Skill   Tool   MCP
                                          │
                                          ↓
                                       Runtime
                                          │
                             ┌────────────┼────────────┐
                             ↓            ↓            ↓
                         Permission     Plugin       Session
                             │            │
                             └──────→ Execution
```

这里的名字并不是说 OpenCode 源码内部一定存在：

```text
InstructionRegistry
CapabilityRegistry
PolicyEngine
PluginRuntime
```

这些组件。

它们只是为了理解架构而做的工程抽象。

这一点非常重要。

因为整个 Harness Marketplace 系列一直遵循同一个原则：

```text
官方文档明确存在
        ↓
可以写成事实

根据行为抽象出来
        ↓
必须说明是工程抽象

内部源码没有公开确认
        ↓
不能假装知道真实类名
```

我们此前已经将这种区分作为整个 Harness Marketplace 系列的重要写作原则。

那么，OpenCode 官方真正暴露出来的静态扩展入口是什么？

可以先记住下面几个关键词：

```text
opencode.json
AGENTS.md

.opencode/
├── agents/
├── commands/
├── skills/
├── tools/
└── plugins/

MCP

permission
```

后面的 OpenCode 系列，基本都会围绕它们展开。

---

# 二、OpenCode 的第一层：配置系统

OpenCode 最核心的配置入口之一是：

```text
opencode.json
```

官方文档同时大量使用：

```text
opencode.jsonc
```

作为带注释的配置示例。

配置中可以出现：

```text
model
provider
agent
permission
mcp
plugin
instructions
watcher
share
...
```

例如 Agent 可以直接定义在：

```json
{
  "$schema": "https://opencode.ai/config.json",

  "agent": {
    "code-reviewer": {
      "description": "Reviews code for best practices",
      "model": "anthropic/claude-sonnet-4-5"
    }
  }
}
```

而 MCP、Plugin 等能力也都可以进入同一个配置体系。

所以从架构上可以先把：

```text
opencode.json
```

理解成：

```text
OpenCode Runtime Configuration
```

它不是 Prompt 文件，也不是 Skill。

它更接近 Harness 的总控配置。

---

## 2.1 配置与能力定义不是一回事

这是第一个很容易混淆的地方。

比如：

```text
opencode.json
```

里面可以配置：

```text
agent
mcp
plugin
permission
```

但这并不意味着：

```text
Agent = Config

Plugin = Config

MCP = Config
```

更准确的理解应该是：

```text
                opencode.json
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
       Runtime     Agent      Plugin
       Config      Config     References
          │          │          │
          └──────────┼──────────┘
                     ↓
                 OpenCode
```

也就是说：

> `opencode.json` 是多个 Runtime 子系统的配置入口，而不是这些能力本身。

这和 Codex 的 `config.toml` 有些类似。

只是 OpenCode 的大量扩展能力比 Codex 更直接地暴露给开发者。

---

# 三、第二层：AGENTS.md——长期 Instruction

如果说 `opencode.json` 管的是：

```text
Harness 怎么运行
```

那么：

```text
AGENTS.md
```

主要解决的是：

```text
Agent 应该遵守什么项目规则
```

OpenCode 官方明确支持项目级：

```text
project/
└── AGENTS.md
```

以及全局：

```text
~/.config/opencode/
└── AGENTS.md
```

项目级 `AGENTS.md` 用于项目规则，全局文件则适用于所有 OpenCode Session。

典型内容可能包括：

```markdown
# Project Rules

## Architecture

- API code lives in packages/api
- Shared models live in packages/core

## Development

- Use Bun
- Run lint before tests

## Code Style

- TypeScript strict mode
- Avoid default exports
```

这些东西有一个共同特点：

> **它们不是一次性任务，而是项目长期有效的约束。**

所以从 Harness 角度：

```text
AGENTS.md
    ↓
Always-on Instruction
```

---

## 3.1 OpenCode 还兼容 CLAUDE.md

这是一个很有意思的设计。

OpenCode 官方提供 Claude Code 文件约定的兼容逻辑。

例如项目目录中如果没有：

```text
AGENTS.md
```

可以回退使用：

```text
CLAUDE.md
```

全局规则也支持：

```text
~/.claude/CLAUDE.md
```

作为兼容来源。

因此可以抽象为：

```text
Current Project
     │
     ↓
 search AGENTS.md
     │
     ├── found
     │      ↓
     │   use it
     │
     └── not found
            ↓
        CLAUDE.md
```

这其实已经暴露出 OpenCode 一个很重要的生态策略：

> **它并不试图把所有能力都锁死在 OpenCode 自己的文件格式里。**

这种兼容性后面在 Skill 上会更加明显。

---

## 3.2 instructions 又是什么？

除了 `AGENTS.md`，OpenCode 还允许在 `opencode.json` 中配置：

```json
{
  "instructions": [
    "CONTRIBUTING.md",
    "docs/guidelines.md",
    ".cursor/rules/*.md"
  ]
}
```

甚至可以使用远程 URL 作为 Instruction 来源。官方说明这些自定义 Instruction 会和 `AGENTS.md` 一起组合进入上下文。

于是 OpenCode 的 Instruction Layer 实际上不是只有：

```text
AGENTS.md
```

而更接近：

```text
                    Instruction Layer
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
         AGENTS.md      CLAUDE.md    instructions[]
             │          fallback         │
             └─────────────┼─────────────┘
                           ↓
                    Agent Context
```

这里和 Codex 的 `AGENTS.md` 会有一个很好的对照点。

后面可以单独用一篇文章研究：

```text
OpenCode 如何发现 Rule
如何处理 fallback
如何向上搜索
如何加载 custom instructions
最终怎么进入 Context
```

---

# 四、第三层：`.opencode/` 才是扩展能力真正集中的地方

如果只是看到：

```text
opencode.json
AGENTS.md
```

还不足以体现 OpenCode 的特色。

真正重要的是：

```text
.opencode/
```

这个目录。

把 OpenCode 当前公开的几种主要扩展能力组合起来，可以得到一棵很典型的项目结构：

```text
project/
│
├── AGENTS.md
├── opencode.json
│
└── .opencode/
    │
    ├── agents/
    │   └── reviewer.md
    │
    ├── commands/
    │   └── test.md
    │
    ├── skills/
    │   └── git-release/
    │       └── SKILL.md
    │
    ├── tools/
    │   └── project.ts
    │
    └── plugins/
        └── security.ts
```

注意：

这棵树是为了把官方文档中的几个扩展入口放在一起展示的**工程化汇总结构**，不是说 OpenCode 官方要求项目必须拥有完整的这些目录。

但从 Harness 视角看，这棵树非常重要。

因为几乎每个目录对应一种不同的 Capability 类型：

| 路径          | 大致职责                                 |
| ----------- | ------------------------------------ |
| `agents/`   | Agent Definition                     |
| `commands/` | User-triggered Workflow              |
| `skills/`   | Agent-triggered Reusable Instruction |
| `tools/`    | Executable Capability                |
| `plugins/`  | Runtime Extension                    |

于是：

```text
.opencode/
```

其实已经非常接近：

```text
Project-level Harness Extension Space
```

---

# 五、第四层：Command——用户主动触发的 Workflow

OpenCode 一个很有特色的能力是：

```text
Command
```

比如：

```text
.opencode/
└── commands/
    └── test.md
```

内容可以写成：

```markdown
---
description: Run tests with coverage
agent: build
model: anthropic/claude-3-5-sonnet-20241022
---

Run the full test suite with coverage report.

Focus on failing tests and suggest fixes.
```

然后用户在 TUI 中输入：

```text
/test
```

即可触发。

OpenCode 官方将 Custom Command 定义为可重复任务的自定义命令，它本质上包装了一个 Prompt Template，并且可以指定 Agent、Model、Subtask 等选项。

所以从架构角度看：

```text
User
 ↓
/test
 ↓
Command
 ↓
Prompt Template
 ↓
Agent
 ↓
Execution
```

这和 Skill 有明显区别。

---

## 5.1 Command 可以先理解为 User-facing Workflow

我们暂时可以这样抽象：

```text
Command
    ↓
User-facing Workflow Entry
```

为什么？

因为它最典型的调用方式是：

```text
/test
/review
/release
```

也就是用户明确告诉 Harness：

> “我要运行这个预定义流程。”

因此：

```text
User
    ↓
Explicit Routing
    ↓
Command
```

这一点后面与 Skill 对比时会非常关键。

---

# 六、第五层：Skill——Agent 按需加载的 Workflow

OpenCode 当前已经有第一方 Agent Skills 支持。

Skill 的目录形式非常熟悉：

```text
.opencode/
└── skills/
    └── git-release/
        └── SKILL.md
```

同时 OpenCode 还会搜索：

```text
~/.config/opencode/skills/

.claude/skills/
~/.claude/skills/

.agents/skills/
~/.agents/skills/
```

这些目录。

这里已经能看到一个很明显的设计思想：

```text
OpenCode native
+
Claude compatible
+
Agent compatible
```

---

## 6.1 Skill 不是 Always-on Instruction

Skill 与 `AGENTS.md` 最大区别是：

```text
AGENTS.md
    ↓
Always-on

Skill
    ↓
On-demand
```

OpenCode 官方明确说明：

Agent 会看到可用 Skill 的名称与描述，但完整内容通过原生：

```text
skill
```

Tool 在需要时加载。

可以把这个过程抽象成：

```text
Discover Skills
      ↓
Expose Metadata
      ↓
Agent sees:

name
description
      ↓
LLM decides
      ↓
skill({
  name: "git-release"
})
      ↓
Load SKILL.md
      ↓
Inject Workflow
```

这就是我们在 Codex 系列里一直强调的：

```text
Progressive Disclosure
```

---

## 6.2 Command 与 Skill第一次可以摆在一起了

到这里，我们已经有：

```text
AGENTS.md
Command
Skill
```

三个非常容易混淆的东西。

可以先这样区分：

```text
AGENTS.md
    ↓
长期规则

Command
    ↓
用户显式调用流程

Skill
    ↓
Agent 按需加载流程
```

进一步抽象：

```text
                Workflow / Instruction
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
      AGENTS.md        Command        Skill
          │              │              │
      Always-on     User Routing    Agent Routing
```

这将是 OpenCode 系列第二、第三篇非常重要的主题。

---

# 七、第六层：Agent——执行者本身也可以被配置

接下来是 Agent。

OpenCode 默认包含诸如：

```text
build
plan
```

这类内置 Agent，同时允许创建自己的 Agent。官方仓库对 `build` 和 `plan` 的默认角色有所说明，例如 `build` 面向开发工作，而 `plan` 偏只读分析。

自定义 Agent 可以直接写在：

```text
opencode.json
```

里。

也可以使用 Markdown：

```text
.opencode/agents/
~/.config/opencode/agents/
```

官方文档同时支持：

```text
primary
subagent
```

这样的 Agent 模式。

例如：

```markdown
---
description: Reviews code for quality
mode: subagent

permission:
  edit: deny
  bash: ask
---

Review the implementation for security,
maintainability and performance.
```

从这里已经能看出：

```text
Agent
```

并不仅仅是一段 System Prompt。

它至少可以绑定：

```text
Agent
├── description
├── mode
├── model
├── prompt
├── tools
└── permission
```

因此用我们的统一 Harness 抽象：

```text
Agent
=
Role
+
Instructions
+
Model
+
Tool Surface
+
Permission
```

会比简单理解为：

```text
Agent = Prompt
```

准确得多。

---

# 八、第七层：Tool——真正执行动作的 Capability

Agent 有了 Workflow，还需要真正操作环境。

这就是：

```text
Tool
```

OpenCode 内置多个 Tool，例如：

```text
bash
edit
write
read
grep
glob
...
```

官方将 Tool 定义为 LLM 可以用来对代码库执行动作的能力，同时支持：

```text
Built-in Tool
Custom Tool
MCP Tool
```

三类扩展来源。

所以 Tool Layer 可以先画成：

```text
                       Tool Surface
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
         Built-in Tool   Custom Tool     MCP
              │             │             │
            bash          project.ts   external
            read          database.ts   server
            edit
            grep
```

这已经非常像一个：

```text
Capability Registry
```

但再次强调：

> “Capability Registry”是我们的架构抽象，不代表 OpenCode 内部一定存在这个名字的类。

---

# 九、Custom Tool：OpenCode 最工程化的扩展入口之一

OpenCode 的 Custom Tool 很值得关注。

它可以直接定义在：

```text
.opencode/tools/
```

或者：

```text
~/.config/opencode/tools/
```

中。

例如：

```ts
import { tool } from "@opencode-ai/plugin"

export default tool({
  description: "Get project information",

  args: {},

  async execute(args, context) {
    return `Project: ${context.worktree}`
  }
})
```

OpenCode 会向 Tool 提供 Session 上下文，包括：

```text
agent
sessionID
messageID
directory
worktree
```

等信息。

于是：

```text
Custom Tool File
      ↓
tool(...)
      ↓
Description
Arguments Schema
Execute Function
      ↓
OpenCode Tool Surface
      ↓
LLM Tool Call
```

这对理解 OpenCode 非常重要。

因为这意味着：

> OpenCode 不只是允许“接外部 MCP”，它还允许开发者直接向 Harness 内部注册可执行能力。

从我们自己的统一模型看：

```text
Custom Tool
    ↓
In-process Capability
```

而：

```text
MCP
    ↓
External Capability Provider
```

二者职责不同。

---

# 十、第八层：MCP——外部能力提供者

OpenCode 同样支持 MCP。

在 `opencode.json` 里可以存在：

```json
{
  "$schema": "https://opencode.ai/config.json",

  "mcp": {
  }
}
```

官方文档明确将 MCP Server 与 Custom Tools 一起列为扩展 Tool Surface 的方式，用于数据库、API 和第三方服务等外部集成。

所以：

```text
MCP Server
    ↓
External Tools
    ↓
OpenCode
    ↓
Tool Surface
    ↓
Agent
```

这和 Custom Tool 是两条不同的路径：

```text
Custom Tool
    ↓
Local / In-process Extension

MCP
    ↓
External Capability Provider
```

如果按照整个 Harness Marketplace 系列的统一语义：

```text
Skill
    → How

Tool
    → What

MCP
    → External Tool Provider
```

这三个概念就开始逐渐分开了。

---

# 十一、第九层：Plugin——这可能才是 OpenCode 真正特殊的地方

如果到 Custom Tool 为止，OpenCode 还只是一个“支持代码扩展的 Coding Agent”。

那么：

```text
Plugin
```

让它开始更像一个真正的：

```text
Programmable Agent Runtime
```

OpenCode Plugin 支持两种主要加载形式。

第一种：

```text
.opencode/plugins/
~/.config/opencode/plugins/
```

直接放：

```text
JavaScript
TypeScript
```

文件。

第二种是在：

```text
opencode.json
```

中配置 npm 包：

```json
{
  "plugin": [
    "opencode-wakatime",
    "@my-org/custom-plugin"
  ]
}
```

官方说明 npm Plugin 会在启动时通过 Bun 自动安装，其包及依赖会被缓存在：

```text
~/.cache/opencode/node_modules/
```

中。

因此可以先画一条：

```text
npm Registry
      ↓
Plugin Package
      ↓
Bun Install
      ↓
Local Cache
      ↓
OpenCode Startup
      ↓
Plugin Load
```

这已经出现了非常明显的：

```text
Distribution
+
Installation
+
Runtime Loading
```

三个阶段。

---

## 11.1 但 Plugin 不只是一个 Package

这也是 OpenCode 和我们前面分析其他 Harness 时最需要小心的地方。

OpenCode Plugin 可以注册 Runtime Hook。

例如官方展示了：

```ts
"tool.execute.before"
```

这样的 Hook，可以在 Tool 执行前读取甚至修改输入。

Plugin 还可以提供：

```text
shell.env
tool.execute.before
tool.execute.after
Custom Tool
...
```

等扩展行为。

因此，如果我们继续简单说：

```text
Plugin
    =
Distribution Package
```

就不够准确了。

对于 OpenCode，更合理的工程抽象是：

```text
OpenCode Plugin
      │
      ├── Runtime Hook
      │
      ├── Custom Tool
      │
      ├── Integration
      │
      └── Programmatic Extension
```

所以：

> OpenCode Plugin 更接近 Runtime Extension Module，而不仅仅是 Capability Distribution Package。

这会是后续 OpenCode Plugin 专篇里最值得展开的问题。

---

# 十二、到这里，OpenCode 已经形成了四种完全不同的“扩展”

现在可以做一次非常关键的整理。

OpenCode 至少存在四类开发者很容易混淆的扩展：

```text
Command
Skill
Tool
Plugin
```

但它们根本不是同一个层面的东西。

可以先这样理解：

| 类型      | 核心职责                |
| ------- | ------------------- |
| Command | 用户触发 Workflow       |
| Skill   | Agent 按需加载 Workflow |
| Tool    | 执行动作                |
| Plugin  | 扩展 Runtime          |

换成一句更简洁的话：

```text
Command
    → Entry

Skill
    → Method

Tool
    → Action

Plugin
    → Extension
```

进一步画出来：

```text
User
 ↓
Command
 ↓
Agent
 │
 ├──────────────→ Skill
 │                  ↓
 │               Workflow
 │
 └──────────────→ Tool
                    ↓
                 Action

Plugin
   │
   └────────────→ Runtime
```

这可能是理解 OpenCode 最重要的一张静态图。

---

# 十三、第十层：Permission——能力存在，不代表允许执行

OpenCode 还有一个很重要的层：

```text
permission
```

当前官方 Permission 系统核心有三种结果：

```text
allow
ask
deny
```

例如：

```json
{
  "$schema": "https://opencode.ai/config.json",

  "permission": {
    "edit": "deny",
    "bash": "ask",
    "webfetch": "allow"
  }
}
```

官方当前文档还支持细粒度 Pattern，例如对特定 Bash 命令、MCP Tool 等配置不同规则。

需要注意的是，OpenCode 当前文档已经说明：

> 从 `v1.1.1` 起，旧版 `tools` 布尔控制被弃用并整合进 `permission`，但旧配置仍保留兼容。

这意味着研究 OpenCode 配置时，不能把不同时期的文档混为一谈。

---

## 13.1 Permission 的意义不是“有没有 Tool”

这是一个很重要的 Harness 设计原则。

假设 Runtime 中已经存在：

```text
bash
git
database_query
skill
mymcp_search
```

这只说明：

```text
Capability Exists
```

却并不说明：

```text
Current Agent Can Use It
```

真正的运行关系应该更接近：

```text
Capability
    ↓
Discovered
    ↓
Available
    ↓
Permission Resolution
    ↓
allow / ask / deny
    ↓
Execution
```

因此：

```text
Capability Definition
        ≠
Permission Grant
```

这一原则在 OpenCode 中表现得非常明显。

甚至 Skill 本身也有独立 Permission。

例如官方支持：

```json
{
  "permission": {
    "skill": {
      "*": "allow",
      "internal-*": "deny",
      "experimental-*": "ask"
    }
  }
}
```

被 `deny` 的 Skill 会对 Agent 隐藏并拒绝访问。

于是：

```text
Skill Installed
      ↓
Skill Discovered
      ↓
Permission
      ↓
Agent Visible?
      ↓
Load?
```

这已经非常接近一个真正的 Capability Policy 系统。

# 十四、OpenCode 的 User Scope 与 Project Scope

现在再回头看目录，就会发现 OpenCode 很多扩展都同时存在两种 Scope：

```text
Global
Project
```

比如 Agent：

```text
~/.config/opencode/agents/
.opencode/agents/
```

Custom Tool：

```text
~/.config/opencode/tools/

```

Plugin：

```text
~/.config/opencode/plugins/
.opencode/plugins/
```

Skill：

```text
~/.config/opencode/skills/
.opencode/skills/
```

Instruction：

```text
~/.config/opencode/AGENTS.md
project/AGENTS.md
```

官方文档对这些 User / Project 路径都有明确说明。

所以可以画出：

```text
                       Scope
                         │
              ┌──────────┴──────────┐
              ↓                     ↓
            User                 Project
              │                     │
 ~/.config/opencode/          project/
```

这说明 OpenCode 已经不是只有：

```text
“配置一个模型然后聊天”
```

这么简单。

它实际上开始出现：

```text

```

这样的 Harness 问题。

# 十五、OpenCode 还体现出一个很强的兼容层思路

OpenCode 静态目录里还有一个很有意思的现象：

它没有完全把扩展生态封闭在：

```text
.opencode/
```

中。

例如 Skill 可以来自：

```text
.opencode/skills/

.claude/skills/

.agents/skills/
```

Instruction 也可以兼容：

```text
CLAUDE.md
```

官方还提供环境变量，用于关闭 Claude Code Prompt 或 Skill 兼容。

于是 OpenCode 的能力发现很可能越来越接近：

```text
Native Convention
        +
Compatibility Convention
        ↓
Unified Runtime Capability
```

从 Harness 生态角度看，这非常值得关注。

因为未来 Agent Harness 之间很可能不会只有：

```text
产品 A 的 Skill
产品 B 的 Skill
产品 C 的 Skill
```

而是逐渐形成：

```text
Common Skill Convention
Common Instruction Convention
Common MCP Protocol
        ↓
Different Harness Runtime
```

OpenCode 对 `.claude/skills` 和 `.agents/skills` 的支持，就是这种趋势的一个明显信号。

# 十七、OpenCode 的扩展体系可以分成五个 Plane

如果进一步抽象，我认为 OpenCode 可以先拆成五层。

## 1. Instruction Plane

```text

```

回答：

> Agent 应该知道什么、遵守什么。

## 2. Workflow Plane

```text

```

回答：

> 一项任务应该按照什么流程完成。

其中：

```text

    → User-triggered

Skill
    → Agent-triggered
```

---

## 3. Execution Plane

```text
Built-in Tool

MCP
```

回答：

> Agent 真正能做什么。

---

## 4. Runtime Extension Plane

```text
Plugin
Hook
Integration
```

回答：

> Harness 自己的行为怎么被扩展。

---

## 5. Policy Plane


回答：

> 已经存在的能力，当前是否允许执行。

```text
     ↓

     ↓

     ↓
```

# 十八、OpenCode 与 Codex 第一眼最大的不同是什么？

这一篇暂时不做完整横向对比。

但为了给 OpenCode 定位，可以先指出一个非常明显的结构差异。

我们此前对 Codex 形成的静态理解大致是：

```text
AGENTS.md
    ↓
Guidance

Skill
    ↓
Workflow

Agent
    ↓
Executor

MCP
    ↓
External Capability

Hook
    ↓
Lifecycle

Policy / Sandbox
    ↓
Enforcement
```

而 OpenCode 现在多了几个非常显式的编程入口：

```text
Command
Custom Tool
TypeScript Plugin
```

于是它的扩展面更像：

```text
Markdown Extension
        +
JSON Configuration
        +
Executable Tool
        +
Programmatic Plugin
```

也就是说：

> OpenCode 不只是允许用户“配置 Harness”，它还明显允许开发者“编程扩展 Harness”。

所以现阶段我更愿意把 OpenCode 工程化地描述为：

```text
Programmable Extensible Agent Runtime
```

注意，这不是 OpenCode 官方产品定义。

而是为了后续比较不同 Harness 的工程抽象。

# 十九、这套结构对自研 Harness 有什么启发？

再次强调：

进一步统一，可以得到：

```text
                  CapabilityDescriptor
                           │
        ┌──────────────────┼──────────────────┐
```

这是一个很重要的设计边界。
