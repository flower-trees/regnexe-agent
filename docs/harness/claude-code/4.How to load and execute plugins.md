# Harness Marketplace 剖析系列 - 之 Claude Code：Harness 如何加载和执行 Plugin 能力

前面的文章已经完成了两层分析。

第一层是 Plugin 的静态结构：

```text
Plugin
├── plugin.json
├── skills/
├── commands/
├── agents/
├── hooks/
├── .mcp.json
└── .lsp.json
```

第二层是 Plugin 从 Marketplace 到本地的安装过程：

```text
Marketplace Entry
    ↓
定位 Plugin Source
    ↓
复制到版本化 Cache
    ↓
写入 enabledPlugins
    ↓
等待 Claude Code 加载
```

但到这里，Plugin 仍然只是一组保存在磁盘上的文件。

真正决定 Plugin 是否有用的是下一步：

> Claude Code Harness 如何把这些文件转化成模型可理解、可选择、可调用的运行时能力？

例如，一个放在：

```text
skills/code-review/SKILL.md
```

中的 Markdown 文件，为什么会出现在 Claude 的可用 Skill 列表中？

一个位于：

```text
agents/security-reviewer.md
```

中的 Agent 定义，又是如何获得独立上下文、工具集合和执行生命周期的？

Plugin 中的：

```text
hooks/hooks.json
.mcp.json
.lsp.json
```

为什么不是简单地进入 Prompt，而是分别接入生命周期事件、外部工具系统和代码智能系统？

这一篇，我们沿着下面这条运行链继续分析：

```text
Plugin 已安装并启用
    ↓
Harness 解析作用域配置
    ↓
定位 Plugin Cache
    ↓
读取 Plugin Manifest
    ↓
发现并注册各类组件
    ↓
构建 Runtime Capability Registry
    ↓
把必要的 Metadata 注入上下文
    ↓
用户显式调用或模型自动匹配
    ↓
执行 Skill / Command / Agent / Hook / MCP / LSP
```

重点回答：

```text
Plugin 在什么时候被扫描？
Skill Metadata 如何进入模型上下文？
Skill 自动匹配是规则路由还是模型判断？
Command 如何展开成实际 Prompt？
Agent 如何创建独立上下文？
Hook、MCP 和 LSP 如何接入 Runtime？
多个 Plugin 的能力如何合并和命名？
/reload-plugins 到底重建了什么？
```

---

# 一、从磁盘文件到运行时能力

要理解 Claude Code 的 Plugin 加载机制，首先需要区分三个不同层次。

```text
第一层：Plugin Files
    → 磁盘上的 Markdown、JSON 和脚本

第二层：Capability Registry
    → Harness 已经识别并注册的能力描述

第三层：Runtime Execution
    → 当前任务真正选择和执行的能力
```

三者并不是一回事。

假设一个 Plugin 中有：

```text
my-plugin/
├── skills/
│   └── review/
│       └── SKILL.md
├── commands/
│   └── review-pr.md
└── agents/
    └── reviewer.md
```

磁盘上出现这些文件，并不等于它们已经全部进入模型上下文。

更准确的过程是：

```text
文件存在
    ↓
Harness 扫描并解析
    ↓
提取组件 Metadata
    ↓
写入运行时能力注册表
    ↓
根据任务按需加载完整内容
```

其中，Claude Code 对不同类型组件采用了不同加载方式。

```text
Skill
    → 先注册描述，匹配后再加载正文

Command
    → 注册显式调用入口，调用时展开正文

Agent
    → 注册独立执行角色，调用时创建子上下文

Hook
    → 注册生命周期监听器，事件发生时执行

MCP
    → 建立外部 Server 连接，注册 Tools 和 Prompts

LSP
    → 启动语言服务器，注册代码导航和诊断能力
```

所以 Plugin Loader 并不是简单地把整个 Plugin 目录拼进 System Prompt。

它更像一个多类型能力装配器：

```text
Plugin Loader
├── Skill Registry
├── Command Registry
├── Agent Registry
├── Hook Dispatcher
├── MCP Server Manager
└── LSP Server Manager
```

# 二、Plugin 在什么时候被扫描

## 1. 首次 Session 启动

当 Claude Code 启动一个新 Session 时，需要先解析当前环境中的 Plugin 配置。

这些配置可能来自：

```text
Managed Settings
User Settings
Project Settings
Local Settings
```

其中 `enabledPlugins` 使用：

```text
plugin-name@marketplace-name
```

作为 Plugin 的完整标识。官方配置文档确认，Plugin 可以在用户级和项目级配置中启用或禁用；如果多个作用域存在配置，Claude Code 会按照其配置作用域规则解析最终状态。

一个典型配置是：

```json
{
  "enabledPlugins": {
    "plugin-dev@claude-plugins-official": true,
    "formatter@company-tools": true,
    "experimental-agent@lab-tools": false
  }
}
```

Harness 首先需要计算：

```text
哪些 Plugin 最终启用
哪些 Plugin 被当前作用域覆盖为禁用
哪些 Plugin 来自 Managed Policy
```

得到启用列表后，才会定位 Plugin 的本地安装目录：

```text
~/.claude/plugins/cache/
└── <marketplace>/
    └── <plugin>/
        └── <version>/
```

---

## 2. Plugin 安装后不会自动修改当前上下文

Plugin 被安装到本地 Cache 后，文件已经存在，但当前 Session 不一定立即感知。

官方 Marketplace 教程在安装 Plugin 后明确要求执行：

```text
/reload-plugins
```

以便在当前 Session 激活新 Plugin。

因此需要区分：

```text
Plugin Installation
    → 改变磁盘状态和配置状态

Plugin Loading
    → 改变当前 Session 的能力状态
```

如果不执行重载，也不重新启动 Session，当前运行时仍可能继续使用旧的能力注册表。

---

## 3. Session 重启时重新加载

重新启动 Claude Code Session 时，Harness 会根据当前配置重新加载已启用 Plugin。

这一过程大致包括：

```text
读取 Settings
    ↓
解析 enabledPlugins
    ↓
定位 Plugin Cache
    ↓
读取 plugin.json
    ↓
发现组件
    ↓
建立 Runtime Registry
```

不过需要说明：

> Anthropic 公开文档描述了 Plugin 的组件加载结果和配置方式，但没有完整公开 Plugin Loader 内部函数级实现。

因此，本文讨论的是根据官方行为和配置规范还原出的逻辑过程，而不是对 Claude Code 二进制内部源码的逐行解读。

---

## 4. Safe Mode 会跳过 Plugin 能力

Claude Code 当前提供：

```bash
claude --safe-mode
```

Safe Mode 会禁用包括 Plugin、Skill、Hook、MCP Server、Custom Command、Agent 和 LSP Server 在内的自定义能力，同时保留内置工具、权限系统和基础认证。

这从另一个角度说明：

```text
Plugin Registry
    → 是 Session 初始化期间装配的独立扩展层

Built-in Runtime
    → 即使没有 Plugin 仍可运行
```

其架构关系可以理解为：

```text
Claude Code Core
    ↓
Built-in Tools / Agent Loop / Permissions
    ↓
Customization Loader
    ├── CLAUDE.md
    ├── Skills
    ├── Commands
    ├── Agents
    ├── Hooks
    ├── MCP
    ├── LSP
    └── Plugins
```

---

# 三、Harness 如何发现 Plugin 中的组件

Claude Code Plugin 采用“标准目录自动发现 + Manifest 补充配置”的模式。

一个典型 Plugin 结构是：

```text
my-plugin/
├── .claude-plugin/
│   └── plugin.json
├── skills/
├── commands/
├── agents/
├── hooks/
│   └── hooks.json
├── .mcp.json
└── .lsp.json
```

Harness 读取 Plugin 后，会根据不同组件类型分别处理。

---

## 1. 读取 `plugin.json`

`plugin.json` 首先提供 Plugin 级身份：

```json
{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "Development utilities"
}
```

它解决的是：

```text
当前目录属于哪个 Plugin
Plugin 的逻辑名称是什么
Plugin 的版本是什么
是否有额外组件声明
```

Marketplace 还支持 `strict` 模式，用于决定 Plugin 自己的 `plugin.json` 与 Marketplace Entry 中的组件定义如何合并。

官方文档说明：

```text
strict = true
    → 默认模式
    → plugin.json 是组件定义权威
    → Marketplace Entry 可以补充组件

strict = false
    → Marketplace Entry 是完整定义
    → 如果 Plugin 自身又声明组件，可能形成冲突
```

这说明 Claude Code 并不总是只扫描 Plugin 目录；在部分 Marketplace 策略中，Marketplace Operator 也可以控制哪些组件实际暴露。

---

## 2. 扫描标准组件目录

在普通 Plugin 中，Harness 会识别：

```text
skills/
commands/
agents/
hooks/hooks.json
.mcp.json
.lsp.json
```

Marketplace 也允许通过配置指向额外的 Command、Agent 或其他组件路径，路径相对于 Plugin Root 解析。

因此，组件来源可能包括：

```text
标准目录自动发现
+
plugin.json 显式配置
+
marketplace.json 补充配置
```

最终形成一个归一化 Plugin Descriptor：

```text
NormalizedPlugin
├── id
├── version
├── rootPath
├── skills[]
├── commands[]
├── agents[]
├── hooks[]
├── mcpServers[]
└── lspServers[]
```

这一步的目标，是把不同来源的目录和配置转成统一的运行时描述。

# 四、Skill Metadata 如何进入上下文

Skill 是 Claude Code Plugin 中最典型的“渐进式上下文能力”。

它的加载过程可以分为两个阶段：

```text
发现阶段
    → 只让 Claude 知道有哪些 Skill

执行阶段
    → 再加载完整 SKILL.md
```

---

## 1. 启动时不加载全部 Skill 正文

官方 Skill 文档明确说明：

> 在普通 Session 中，Skill 的描述会被加载到上下文，使 Claude 知道当前有哪些 Skill；完整 Skill 内容只有在 Skill 被调用时才加载。

因此，假设有三个 Skill：

```text
skills/
├── code-review/
│   └── SKILL.md
├── database-migration/
│   └── SKILL.md
└── release-management/
    └── SKILL.md
```

Session 启动时，Claude 看到的更接近：

```text
Available Skills:

- code-review:
  Review code for correctness, security and maintainability.

- database-migration:
  Plan and execute safe database schema migrations.

- release-management:
  Prepare, validate and publish software releases.
```

而不是一次性加载三个 Skill 的完整正文。

---

## 2. Metadata 来自 Frontmatter

一个 Skill 通常包含：

```yaml
---
name: database-migration
description: Use this skill when planning, reviewing or executing database schema migrations.
---
```

Harness 会解析：

```text
name
description
以及其他与触发、工具和执行方式有关的 Frontmatter
```

其中最重要的是 `description`。

它不仅用于 UI 展示，还承担 Skill 发现和路由作用。

可以把启动阶段抽象为：

```text
扫描 skills/*/SKILL.md
    ↓
解析 Frontmatter
    ↓
提取 name + description
    ↓
加入 Skill Catalog
    ↓
把 Catalog 摘要提供给模型
```

---

## 3. 为什么只加载 Metadata

假设一个 Plugin 有 20 个 Skills，每个 Skill 包含：

```text
3 KB SKILL.md
20 KB References
10 KB Examples
```

全部加载可能达到：

```text
20 × 33 KB
=
660 KB 上下文
```

其中大部分内容与当前任务无关。

所以 Skill 系统采用：

```text
Metadata Always Available
+
Full Instructions On Demand
+
References When Needed
```

其价值是：

```text
降低初始 Token 成本
减少无关知识干扰
允许安装更多 Skill
提高上下文利用率
```

这也是 Claude Code Skill 体系能够扩展成 Marketplace 生态的前提。

# 五、Skill 如何被自动匹配

Skill 的自动匹配并不是一个传统的硬编码 Intent Router。

更准确的描述是：

```text
Skill Metadata 进入模型上下文
    ↓
模型阅读用户请求
    ↓
模型判断某个 Skill 是否相关
    ↓
调用或加载该 Skill
```

---

## 1. `description` 是模型路由提示

例如：

```yaml
---
name: java-code-review
description: Use this skill when reviewing Java or Spring Boot code for correctness, security, concurrency issues, transaction handling and maintainability.
---
```

用户提出：

```text
帮我检查这个 Spring Boot Service，
重点看看事务和并发有没有问题。
```

模型可以通过语义理解判断：

```text
用户请求：
Spring Boot + 事务 + 并发检查

Skill Description：
Java / Spring Boot + concurrency + transaction

匹配度较高
    ↓
加载 java-code-review Skill
```

它不是简单的关键词正则。

即使用户没有说“使用 java-code-review”，模型仍可能自动选择。

---

## 2. 自动匹配不是强保证

因为它依赖模型判断，所以存在：

```text
应该触发但没有触发
不应该触发却误触发
多个相似 Skill 同时竞争
Skill Description 过宽导致频繁加载
```

因此，Skill Description 应尽量说明：

```text
什么时候应该使用
适用于哪些任务
不适用于哪些任务
能够解决什么问题
```

而不是只写：

```yaml
description: Helps with code.
```

后者无法提供足够的路由信息。

---

## 3. 用户可以显式调用 Skill

除了自动匹配，用户还可以通过 `/` 菜单或 Slash 形式直接调用 Skill。

Claude Code 的交互界面会把内置命令、用户 Skill、项目 Skill、Plugin Skill 以及 MCP 提供的 Prompt 统一展示在 `/` 菜单中。

Plugin Skill 通常使用命名空间：

```text
/plugin-name:skill-name
```

例如：

```text
/quality-review-plugin:quality-review
```

官方 Marketplace 教程明确展示了这种调用方式。

因此 Skill 有两种入口：

```text
自动入口
    → 模型根据 Description 判断

显式入口
    → 用户使用 /plugin:skill
```

---

## 4. Skill 被调用后的展开

当用户显式调用 Skill：

```text
/fix-issue 123
```

Claude Code 会把 Skill 内容展开为发送给 Claude 的实际指令。

官方 Skill 文档给出的行为是：

```text
Skill 模板：
Fix GitHub issue $ARGUMENTS following our coding standards.

用户输入：
/fix-issue 123

展开结果：
Fix GitHub issue 123 following our coding standards.
```

如果 Skill 没有使用 `$ARGUMENTS`，Claude Code 会把用户参数附加到 Skill 内容末尾，使模型仍能看到输入。

所以 Skill 调用不是传统函数调用：

```java
skill.execute(123);
```

而更接近：

```text
Skill Markdown
+
用户参数
    ↓
Prompt Expansion
    ↓
进入当前 Agent 上下文
```

---

# 六、Command 如何展开为 Prompt

Claude Code 早期将 Slash Command 和 Skill 视为较为独立的概念；当前 `/` 菜单中会统一展示可调用的内置命令、Skill、Plugin Command 和 MCP Prompt。

但从运行机制看，仍然可以把 Plugin Command 理解为：

> 用户显式触发的一段任务入口 Prompt。

---

## 1. Command 注册阶段

Harness 扫描：

```text
commands/
└── review-pr.md
```

提取：

```text
Command 名称
描述
参数规则
正文模板
允许的工具或执行方式
```

并注册成：

```text
/plugin-name:review-pr
```

此时只是建立入口，并不会自动执行正文。

---

## 2. 用户调用阶段

用户输入：

```text
/my-plugin:review-pr 128
```

Harness 会：

```text
定位 my-plugin:review-pr
    ↓
读取 review-pr.md
    ↓
解析 Frontmatter
    ↓
替换参数
    ↓
生成展开后的用户指令
    ↓
进入当前 Agent Turn
```

可以抽象成：

```text
Command Template
+
User Arguments
+
Current Context
    =
Expanded Prompt
```

---

## 3. Command 不是独立进程

Command 默认仍运行在当前主 Agent 上下文中。

因此它可以利用：

```text
当前会话历史
CLAUDE.md
已经加载的文件
当前工具集合
当前项目环境
```

这与 Subagent 不同。

```text
Command
    → 改变当前 Turn 的任务指令

Subagent
    → 创建一个新的执行上下文
```

---

## 4. Command 可以继续触发其他能力

Command 正文可以要求 Claude：

```text
读取某个 Skill
委托某个 Agent
调用 MCP Tool
运行脚本
检查测试结果
```

所以一个 Command 可以成为能力编排入口：

```text
/plugin:create-release
    ↓
加载 release Skill
    ↓
调用 changelog Agent
    ↓
调用 GitHub MCP
    ↓
触发测试 Hook
```

不过这些关系大部分仍由自然语言描述，而不是结构化 DAG 强制执行。

---

# 七、Agent 如何创建独立上下文

Plugin Agent 与 Skill、Command 最大的区别是：

> Agent 不是把更多指令加入当前上下文，而是创建一个独立的执行上下文。

官方 Subagent 文档明确说明，每个 Subagent 都运行在自己的 Context Window 中，可以拥有自定义 System Prompt、特定工具访问权限和独立权限设置。

---

## 1. Agent 注册阶段

Harness 扫描：

```text
agents/
└── security-reviewer.md
```

解析其 Frontmatter 和正文，例如：

```yaml
---
name: security-reviewer
description: Review code for security vulnerabilities.
tools:
  - Read
  - Grep
  - Bash
maxTurns: 15
---

You are a security-focused code reviewer...
```

注册后形成：

```text
plugin-name:security-reviewer
```

在这一阶段，Harness 主要保存的是 Agent Definition：

```text
AgentDefinition
├── name
├── description
├── systemPrompt
├── model
├── tools
├── skills
├── maxTurns
└── isolation
```

---

## 2. Agent 调用阶段

当主 Agent 决定委托：

```text
请让 security-reviewer 检查登录模块。
```

Harness 会创建新的子任务执行环境：

```text
Main Agent
    ↓
创建 Subagent Invocation
    ↓
建立独立 Context Window
    ↓
注入 Agent System Prompt
    ↓
注入任务描述
    ↓
提供允许的工具和 Skill
    ↓
启动独立 Agent Loop
```

这个 Subagent 不会默认获得主 Agent 的全部聊天历史。

它通常获得的是：

```text
专用 System Prompt
当前委托任务
必要的项目环境
允许的工具
明确传递的文件或上下文
```

---

## 3. 为什么需要独立上下文

假设代码审查任务需要读取：

```text
50 个文件
大量 grep 结果
多轮测试输出
依赖分析结果
```

如果全部在主 Agent 上下文中执行，会造成：

```text
主上下文快速膨胀
中间工具轨迹污染最终推理
多个子任务相互干扰
长任务更容易触发压缩
```

独立 Agent 可以把这些中间过程隔离：

```text
Main Agent
    ↓
Security Reviewer
    ├── 阅读大量代码
    ├── 搜索漏洞模式
    ├── 运行检查
    └── 返回简洁结论
    ↓
Main Agent 只接收结果摘要
```

这是一种典型的 Context Quarantine。

---

## 4. Agent 仍受 Harness 权限约束

Plugin Agent 可以声明自己希望使用的工具，但最终可用权限仍由 Harness 的上层策略决定。

合理的权限计算是：

```text
Agent 请求工具
    ∩
Plugin 可用工具
    ∩
项目 Permission
    ∩
用户 / Managed Policy
    =
最终 Agent Tools
```

Agent 可以缩小自己的权限，但不能通过 Frontmatter 扩大系统权限。

这也是前面番外篇分析的核心：

```text
Agent 决定怎样工作
Harness 决定允许它做什么
```

---

# 八、Hook 如何接入生命周期 Runtime

Skill、Command 和 Agent 主要围绕模型上下文工作。

Hook 则不同。

Hook 接入的是 Claude Code 的生命周期事件系统。

官方 Hook 文档将 Hook 定义为在 Claude Code 特定生命周期节点自动执行的 Shell Command、HTTP Endpoint 或 LLM Prompt。

---

## 1. Plugin Hook 的加载

Plugin 可以提供：

```text
hooks/
└── hooks.json
```

例如：

```json
{
  "description": "Format files after edits",
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PLUGIN_ROOT}/scripts/format.sh"
          }
        ]
      }
    ]
  }
}
```

Plugin 启用后，它的 Hook 会与用户和项目 Hook 合并。

因此 Hook 的加载过程是：

```text
读取 Plugin hooks.json
    ↓
解析 Event + Matcher + Handler
    ↓
加入全局 Hook Registry
    ↓
对应事件触发时执行
```

---

## 2. Hook 不需要模型主动选择

假设 Hook 监听：

```text
PostToolUse
matcher = Write|Edit
```

那么每次 `Write` 或 `Edit` Tool 执行后，Hook Dispatcher 都会检查并执行对应处理器。

流程是：

```text
Agent 调用 Edit
    ↓
PreToolUse Hooks
    ↓
Permission Check
    ↓
执行 Edit
    ↓
PostToolUse Hooks
    ↓
继续 Agent Loop
```

官方 Hook 生命周期包含 Session、Turn、Tool Call、Subagent、Compact、Config Change 等多类事件。

所以 Hook 是：

```text
Event-driven Runtime Extension
```

而不是：

```text
Prompt-driven Context Extension
```

---

## 3. Hook 可以影响执行结果

Hook 不只是执行旁路脚本。

根据 Hook 类型和事件，它可以：

```text
允许或阻止工具调用
修改部分输入
返回决策
追加上下文
发送 HTTP 请求
启动异步任务
记录审计日志
```

因此 Hook Registry 是 Claude Code Runtime 的重要组成部分。

它与 Skill Registry 的区别是：

```text
Skill Registry
    → 服务于模型能力发现

Hook Registry
    → 服务于生命周期事件分发
```

---

# 九、MCP 如何接入工具 Runtime

Plugin MCP Server 的作用，是把外部能力转化为 Claude Code Tool 和 Prompt。

Plugin 可以在根目录提供：

```text
.mcp.json
```

也可以在 `plugin.json` 中内联 `mcpServers`。

---

## 1. MCP Server 的启动

例如：

```json
{
  "mcpServers": {
    "database-tools": {
      "command": "${CLAUDE_PLUGIN_ROOT}/servers/db-server",
      "args": ["--config", "${CLAUDE_PLUGIN_ROOT}/config.json"],
      "env": {
        "DB_URL": "${DB_URL}"
      }
    }
  }
}
```

Plugin 启用后，Claude Code 会自动连接其 MCP Server。

流程是：

```text
读取 .mcp.json
    ↓
解析 Server Definition
    ↓
替换 CLAUDE_PLUGIN_ROOT 等变量
    ↓
启动 stdio / HTTP / SSE / WS Server
    ↓
执行 MCP Initialize
    ↓
发现 Tools / Prompts / Resources
    ↓
加入 Runtime
```

---

## 2. MCP Tool 如何命名

Plugin MCP Tool 需要避免与用户手工配置的 MCP、其他 Plugin MCP 发生冲突。

官方 MCP 文档给出的完整工具名形式是：

```text
mcp__plugin_<plugin-name>_<server-name>__<tool-name>
```

例如：

```text
Plugin：
my-plugin

Server：
database-tools

Tool：
query
```

最终工具名：

```text
mcp__plugin_my-plugin_database-tools__query
```

对应 Server 的作用域名称则是：

```text
plugin:my-plugin:database-tools
```

这说明 MCP 能力使用了比 Skill 更完整的命名空间：

```text
Plugin
+
Server
+
Tool
```

---

## 3. MCP Tool 进入模型工具列表

MCP Server 完成连接后，其 Tools 会与 Claude Code 内置 Tools 和其他 MCP Tools 一起提供给模型。

```text
Built-in Tools
├── Read
├── Write
├── Edit
└── Bash

User MCP Tools
└── mcp__github__create_issue

Plugin MCP Tools
└── mcp__plugin_my-plugin_database-tools__query
```

模型随后可以在 Agent Loop 中产生 MCP Tool Call。

这与 Skill 的加载机制不同：

```text
Skill
    → 作为指令内容进入上下文

MCP Tool
    → 作为结构化 Tool Schema 进入工具列表
```

---

## 4. MCP Prompt 也可以成为 `/` Command

MCP Server 可以暴露 Prompt。

Claude Code 会把这些 Prompt 注册到 `/` 菜单中，命名形式为：

```text
/mcp__servername__promptname
```

因此，`/` 菜单实际上合并了多种来源：

```text
Built-in Commands
User Skills
Project Skills
Plugin Skills
Plugin Commands
MCP Prompts
```

这也是为什么用户界面上看起来都像 Slash Command，但背后执行机制并不相同。

---

# 十、LSP 如何接入代码智能 Runtime

LSP 与 Skill、Command、Agent、Hook 和 MCP 都不同。

它不直接增加 Prompt，也不提供普通业务 Tool，而是向 Claude Code 提供结构化代码理解能力。

Plugin 可以通过 LSP 配置声明语言服务器。官方 Marketplace 文档将 LSP Server 列为 Plugin 可以携带的正式组件。

---

## 1. LSP Server 的加载目标

当 LSP Plugin 被启用后，Claude Code 需要完成：

```text
读取 LSP 配置
    ↓
识别语言和文件扩展名
    ↓
启动 Language Server
    ↓
执行 initialize
    ↓
建立文件与 Server 映射
    ↓
注册代码智能能力
```

代码智能能力可能包括：

```text
Document Symbols
Hover
Go to Definition
Find References
Diagnostics
Type Errors
```

官方成本优化文档指出，代码智能 Plugin 可以让 Claude 使用精确符号导航替代大量文本搜索，并在编辑后自动获得类型错误诊断。

---

## 2. LSP 能力如何参与 Agent Loop

没有 LSP 时，Claude 查找一个符号可能需要：

```text
Grep
    ↓
读取多个候选文件
    ↓
分析哪个是定义
```

有 LSP 时，可以变成：

```text
Go To Definition
    ↓
直接返回符号位置
```

因此，LSP 的价值不是单纯增加一个命令，而是改变代码探索方式：

```text
Text Search Based Exploration
    ↓
Semantic Code Navigation
```

---

## 3. LSP 配置的实现仍需谨慎验证

与 Skill、Hook、MCP 相比，Claude Code 的 LSP Plugin 在不同版本中出现过配置加载和初始化相关问题。

Anthropic GitHub Issues 中存在 `.lsp.json`、`plugin.json` 与 Marketplace Entry 之间加载差异，以及部分字段虽然通过 Schema、却导致 Server 未注册的问题。

因此在写 LSP Plugin 时，应该区分：

```text
官方规范声明支持什么
当前 Claude Code 版本实际加载什么
某些配置字段是否真正生效
```

不能仅凭 Schema 合法就推断运行时一定成功。

比较可靠的验证方式是检查：

```text
Plugin 是否被加载
LSP Server 是否被注册
Server 是否成功启动
文件扩展名是否映射
Hover / Definition / Diagnostics 是否真正返回结果
```

---

# 十一、多个 Plugin 的能力如何合并和命名

当用户安装多个 Plugin 后，Harness 面临一个问题：

```text
不同 Plugin 可能定义同名 Skill
不同 Plugin 可能定义同名 Command
不同 Plugin 可能定义同名 Agent
不同 MCP Server 可能提供同名 Tool
```

如果全部使用裸名称，冲突几乎不可避免。

Claude Code 的核心解决方式是：

> 使用 Plugin 命名空间。

---

## 1. Plugin Skill 命名

Plugin Skill 使用：

```text
/plugin-name:skill-name
```

例如：

```text
/plugin-dev:plugin-structure
/quality-review-plugin:quality-review
```

---

## 2. Plugin Command 命名

Plugin Command 同样使用：

```text
/plugin-name:command-name
```

例如：

```text
/plugin-dev:create-plugin
/git-tools:create-release
```

---

## 3. Plugin Agent 命名

Plugin Agent 通常以：

```text
plugin-name:agent-name
```

进行作用域区分。

例如：

```text
plugin-dev:plugin-validator
security-tools:code-reviewer
```

---

## 4. Plugin MCP Tool 命名

MCP Tool 使用更完整的结构：

```text
mcp__plugin_<plugin>_<server>__<tool>
```

它同时隔离：

```text
Plugin
MCP Server
Tool
```

---

## 5. Hook 不依赖用户调用名称

Hook 主要通过：

```text
Event
+
Matcher
```

进行合并。

例如多个 Plugin 都监听：

```text
PostToolUse
```

Harness 会将对应 Handler 合并到同一事件注册表中。

因此 Hook 冲突主要不是名称冲突，而是行为冲突：

```text
多个 Formatter 重复执行
一个 Hook 允许、另一个 Hook 阻止
多个 Hook 修改同一输入
执行顺序影响最终结果
```

---

## 6. 能力注册表的逻辑结构

多个 Plugin 加载后，Harness 中的能力集合可以抽象为：

```text
RuntimeCapabilityRegistry
├── skills
│   ├── plugin-a:review
│   └── plugin-b:review
│
├── commands
│   ├── plugin-a:release
│   └── plugin-b:release
│
├── agents
│   ├── plugin-a:reviewer
│   └── plugin-b:reviewer
│
├── hooks
│   └── Event → Handlers[]
│
├── mcpServers
│   ├── plugin:plugin-a:github
│   └── plugin:plugin-b:database
│
└── lspServers
    └── Language / Extension → Server
```

这并不是 Anthropic 公开的内部类名，而是对其运行行为的工程化抽象。

---

# 十二、不同作用域的能力如何进入 Registry

Plugin 可以在不同作用域启用：

```text
Managed
User
Project
Local
```

Harness 不能简单地把所有配置相加，因为可能出现：

```text
User Scope：
formatter = true

Project Scope：
formatter = true

Local Scope：
formatter = false
```

所以在扫描 Plugin 前，需要先进行配置解析：

```text
收集各 Scope 配置
    ↓
应用作用域优先级
    ↓
确定最终 enabledPlugins
    ↓
再加载对应 Plugin
```

能力本身通常使用统一 Plugin Cache，不会因为 Scope 不同就重复注册多份。

因此：

```text
Scope
    → 决定 Plugin 是否启用

Plugin Namespace
    → 决定能力如何命名

Plugin Cache
    → 决定从哪个版本目录加载
```

---

# 十三、`/reload-plugins` 到底重建了什么

`/reload-plugins` 不是简单地重新读取一个 JSON 文件。

它更接近：

> 在当前 Session 中重新同步磁盘 Plugin 状态与运行时能力注册表。

官方 Marketplace 文档明确将 `/reload-plugins` 用于在当前 Session 中激活新安装 Plugin。

---

## 1. 为什么需要 Reload

Plugin 状态可能发生变化：

```text
安装了新 Plugin
更新了 Plugin 版本
启用了已禁用 Plugin
禁用了当前 Plugin
修改了本地 Plugin
新增了 Skill
新增了 Agent
修改了 MCP 配置
```

而当前 Session 中仍保留着旧 Registry：

```text
Current Session Registry
    ≠
Current Disk State
```

`/reload-plugins` 的目标就是重新对齐两者。

---

## 2. 可能涉及的重载步骤

逻辑上可以还原为：

```text
读取最新 enabledPlugins
    ↓
比较当前已加载 Plugin
    ↓
卸载已禁用或已删除 Plugin 能力
    ↓
定位新 Plugin / 新版本 Cache
    ↓
重新读取 Manifest
    ↓
重新扫描 Skill / Command / Agent
    ↓
重新合并 Hook
    ↓
连接或断开 MCP Server
    ↓
重新处理 LSP Server
    ↓
重建 Capability Registry
```

其中 MCP 有一个重要优化：

官方文档说明，执行 Plugin 重载时，如果某个 Plugin MCP Server 的配置没有变化，Claude Code 会保留其现有连接；配置发生变化或 Plugin 被禁用时，才连接、断开或替换。

因此 Reload 不一定意味着：

```text
所有 MCP Server 全部关闭再重启
```

更可能是增量同步。

---

## 3. Reload 对上下文的影响

当 Skill Catalog 变化时，模型需要知道新的能力描述。

所以 Reload 后，后续模型请求使用的可用 Skill Metadata 也会发生变化。

例如：

```text
Reload 前：
Skills = 10

安装 Plugin 后：
Disk Skills = 17

Reload 后：
Runtime Skills = 17
```

当前已经发送给模型的历史消息不会被重写，但后续 Turn 构建上下文时，会基于新的能力集合。

---

## 4. Reload 与 Session Restart 的区别

```text
/reload-plugins
    → 在当前 Session 中刷新 Plugin 能力
    → 尽可能保留当前对话历史

Restart Session
    → 完整重新初始化 Session
    → 重新加载全部配置与上下文
```

如果只是：

```text
新增 Skill
启用 Plugin
更新 Command
```

通常可以先尝试 `/reload-plugins`。

如果涉及：

```text
复杂 Hook 状态
异常 MCP 进程
LSP 初始化失败
Plugin 配置冲突
Session 内部状态异常
```

重新启动 Session 往往更彻底。

# 十四、不同组件的执行模型对比

到这里，可以把六类 Plugin 能力放在一起比较。

| 组件      | 注册内容                    | 触发方式                     |          是否进入模型上下文 |     是否独立上下文 |
| ------- | ----------------------- | ------------------------ | -----------------: | ----------: |
| Skill   | Metadata + Instructions | 自动匹配或显式调用                |                  是 |         默认否 |
| Command | Prompt Template         | 用户显式调用                   |                  是 |         默认否 |
| Agent   | Agent Definition        | 模型委托或用户调用                |         任务指令进入子上下文 |           是 |
| Hook    | Event Handler           | 生命周期事件                   |                不一定 | 取决于 Hook 类型 |
| MCP     | Tool/Prompt Schema      | 模型 Tool Call或用户调用 Prompt | Tool Schema 进入工具列表 | Server 独立运行 |
| LSP     | Language Server 能力      | 代码导航或诊断需求                |         通常不以正文形式进入 | Server 独立运行 |

这张表揭示了 Claude Code Plugin 的本质：

```text
Plugin 并不是一种能力
而是多种能力模型的统一包装
```

# 十五、完整执行链案例

假设安装了一个完整的 Java Review Plugin：

```text
java-review/
├── skills/
│   └── spring-review/
├── commands/
│   └── review-service.md
├── agents/
│   └── transaction-reviewer.md
├── hooks/
│   └── hooks.json
├── .mcp.json
└── .lsp.json
```

用户输入：

```text
/java-review:review-service OrderService
```

完整运行链可能是：

```text
用户显式调用 Command
    ↓
Harness 展开 review-service.md
    ↓
Prompt 进入主 Agent 上下文
    ↓
主 Agent 匹配 spring-review Skill
    ↓
加载 SKILL.md
    ↓
需要深入检查事务
    ↓
委托 transaction-reviewer Agent
    ↓
创建独立 Context
    ↓
Agent 调用 Java LSP 查找定义和引用
    ↓
Agent 调用 Database MCP 查询表结构
    ↓
工具调用前后触发 Plugin Hooks
    ↓
Agent 返回事务风险结论
    ↓
主 Agent 合并结果
    ↓
生成最终审查报告
```

其中每个组件的职责是：

```text
Command
    → 启动任务

Skill
    → 提供审查方法

Agent
    → 隔离执行专业子任务

LSP
    → 提供代码语义导航

MCP
    → 提供外部数据库能力

Hook
    → 在执行过程中自动检查和记录
```

这就是 Plugin 从文件包转化为运行时能力组合的完整过程。

# 十六、从加载机制看 Claude Code Harness 的设计

通过前面的分析，可以总结出 Claude Code Harness 的几个核心特点。

## 1. 不同能力使用不同注册表

Claude Code 没有把所有 Plugin 文件统一变成 Prompt。

而是分别进入：

```text
Skill Catalog
Command Registry
Agent Registry
Hook Dispatcher
MCP Tool Registry
LSP Server Registry
```

这是一个多运行时扩展架构。

---

## 2. 上下文能力采用渐进加载

Skill 只先加载 Metadata，正文按需进入上下文。

```text
Always-on Metadata
+
On-demand Instructions
```

这样可以控制 Token 成本。

---

## 3. 显式调用和模型匹配并存

```text
Skill
    → 可自动匹配，也可显式调用

Command
    → 主要显式调用

Agent
    → 可自动委托，也可显式选择

MCP Tool
    → 模型自动调用

MCP Prompt
    → 用户显式调用
```

Harness 同时支持用户控制和 Agent 自主性。

---

## 4. Plugin Namespace 是能力隔离基础

多个 Plugin 能够共存，主要依赖：

```text
plugin-name:component-name
```

以及 MCP 的多级命名空间。

这避免了大量名称冲突，也保留了能力来源信息。

---

## 5. Context Runtime 与 Service Runtime 并存

```text
Skill / Command
    → 主要属于 Context Runtime

Agent
    → 属于独立 Agent Runtime

Hook
    → 属于 Event Runtime

MCP
    → 属于 Tool Service Runtime

LSP
    → 属于 Code Intelligence Runtime
```

所以 Claude Code Plugin 并不是简单的 Prompt 插件系统，而是一个多运行时 Capability Package。

---

# 十七、这套加载机制的优势

## 1. Plugin 可以非常灵活

一个 Plugin 可以只提供一个 Skill，也可以同时提供：

```text
Skill
Command
Agent
Hook
MCP
LSP
```

## 2. 初始上下文成本较低

通过只注入 Skill Metadata，避免把所有 Skill 正文一次性加载。

## 3. 能力来源可追踪

命名空间保留了 Plugin 来源：

```text
plugin-dev:plugin-validator
```

## 4. 外部能力能够自动装配

安装 Plugin 后，MCP 和 LSP 可以随 Plugin 一起分发和启动，不需要用户逐项手动配置。

## 5. 当前 Session 支持动态重载

通过 `/reload-plugins`，安装新能力后不一定需要完全退出当前对话。

---

# 十八、这套加载机制的局限

## 1. Skill 路由依赖模型判断

Skill Description 的质量直接影响自动匹配效果。

## 2. 组件关系缺乏结构化声明

Command、Skill 和 Agent 的依赖大量隐藏在自然语言中。

## 3. Runtime Registry 不完全透明

用户能看到加载结果，但 Claude Code 没有公开完整的统一 Capability Registry 数据结构。

## 4. Hook 合并可能产生行为冲突

多个 Plugin 监听同一事件时，执行顺序和决策冲突需要谨慎处理。

## 5. MCP 会增加工具上下文

大量 MCP Tools 会扩大模型工具列表，影响工具选择和 Token 成本。

## 6. LSP 实际兼容性仍受版本影响

部分 LSP 配置在不同版本中存在“Schema 支持但 Runtime 不生效”的情况，需要进行真实运行验证。

## 7. Reload 不等于完整冷启动

某些复杂状态问题仍可能需要重启 Session 才能完全解决。

---

# 十九、对自研 Harness 的启发

如果设计自己的 Harness Marketplace，可以借鉴 Claude Code 的多注册表模型。

```text
PluginLoader
    ↓
NormalizedPluginDescriptor
    ↓
CapabilityRegistries
    ├── SkillRegistry
    ├── CommandRegistry
    ├── AgentRegistry
    ├── HookRegistry
    ├── ToolRegistry
    └── LanguageServiceRegistry
```

同时可以增加更强的结构化描述。

例如：

```yaml
plugin:
  name: java-review

capabilities:
  skills:
    - id: spring-review
      entry: skills/spring-review/SKILL.md
      autoMatch: true

  commands:
    - id: review-service
      entry: commands/review-service.md
      requires:
        - skill:spring-review

  agents:
    - id: transaction-reviewer
      entry: agents/transaction-reviewer.md
      requires:
        - tool:java-lsp
        - tool:database-query

  hooks:
    - event: PostToolUse
      entry: hooks/validate-edit.sh
```

这样可以让 Harness 明确知道：

```text
Command 依赖哪些 Skill
Agent 需要哪些 Tool
哪些组件允许自动触发
哪些能力必须显式调用
```

进一步还可以提供统一的调试命令：

```text
/capabilities list
/capabilities inspect plugin-dev
/capabilities trace current-turn
/capabilities reload
```

让用户看到：

```text
哪些 Plugin 被加载
每个能力来自哪里
某个 Skill 为什么被匹配
某个 Agent 为什么获得这些工具
某个 Hook 在什么时候运行
```

# 总结

Claude Code Plugin 从磁盘文件变成运行时能力，并不是一个简单的“读取目录并拼接 Prompt”过程。

它经过了一套分层装配机制：

```text
Settings
    ↓
确定启用 Plugin
    ↓
定位 Plugin Cache
    ↓
读取 Manifest
    ↓
发现标准组件
    ↓
分别注册到不同 Runtime
```

不同组件的转化方式分别是：

```text
SKILL.md
    → Skill Metadata
    → Skill Catalog
    → 匹配后加载完整 Instructions

Command Markdown
    → Slash Command Registry
    → 用户调用后展开 Prompt

Agent Markdown
    → Agent Registry
    → 调用时创建独立 Context Window

hooks.json
    → Hook Registry
    → 生命周期事件触发执行

.mcp.json
    → MCP Server Manager
    → 注册 Tools 和 Prompts

.lsp.json
    → LSP Server Manager
    → 注册代码导航和诊断能力
```

多个 Plugin 则通过命名空间合并：

```text
plugin-name:skill-name
plugin-name:command-name
plugin-name:agent-name

mcp__plugin_<plugin>_<server>__<tool>
```

`/reload-plugins` 所做的，也不只是重新读取文件，而是：

```text
重新解析 Plugin 状态
    ↓
同步启用与禁用变化
    ↓
重新扫描组件
    ↓
更新 Skill / Command / Agent Registry
    ↓
合并 Hook
    ↓
连接或断开 MCP
    ↓
更新 LSP
    ↓
重建当前 Session 的能力集合
```

从架构角度看，Claude Code Plugin 的本质可以概括为：

```text
Plugin
=
Context Extension
+
Agent Extension
+
Event Extension
+
Tool Extension
+
Code Intelligence Extension
```

也正因为如此，Claude Code Marketplace 分发的不只是一些 Prompt，而是一组可以改变 Harness 运行时能力边界的完整扩展包。
