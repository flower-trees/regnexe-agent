# Harness Marketplace 剖析系列 - 之 Claude Code：一个真实 Plugin 与 Skill 的完整拆解

前两篇中，我们已经分别分析了：

```text
第一篇：
Claude Code 的目录与配置结构

第二篇：
Marketplace 如何发现、安装和落盘
```

经过前面的分析，一个 Marketplace 中的 Plugin 最终会被复制到 Claude Code 的本地版本化缓存中：

```text
~/.claude/plugins/cache/
└── claude-plugins-official/
    └── plugin-dev/
        └── <version>/
```

但文件落盘只是开始。

接下来更关键的问题是：

> 一个安装完成的 Claude Code Plugin，究竟向 Harness 提供了什么？

它只是一个存放 Prompt 的目录，还是一个能够同时注册 Skill、Command、Subagent、Hook、MCP Server 等多种能力的扩展包？

这一篇，我们选择 Anthropic 官方 Marketplace 中的 `plugin-dev`，沿着下面这条链路进行完整拆解：

```text
marketplace.json
    ↓
Plugin Source
    ↓
本地 Plugin 目录
    ↓
plugin.json
    ↓
skills / commands / agents
    ↓
组件之间的协作
    ↓
Claude Code Harness 自动发现
    ↓
运行时能力注册
```

重点回答以下问题：

```text
Marketplace Entry 负责什么？
plugin.json 为什么非常精简？
Skill、Command 和 Agent 分别解决什么问题？
References、Examples 和 Scripts 如何参与执行？
没有 hooks、MCP 和 LSP 配置意味着什么？
这些文件最终如何变成 Harness 中的真实能力？
```

# 一、为什么选择 `plugin-dev`

Anthropic 官方 Marketplace 中提供了多种不同类型的 Plugin，例如：

```text
code-review
commit-commands
code-simplifier
pr-review-toolkit
skill-creator
plugin-dev
```

其中，`plugin-dev` 的定位是：

> 一套用于开发 Claude Code Plugin 的完整能力工具包。

它不是一个只解决单一任务的 Skill，而是围绕“Plugin 开发”这个领域，组织了一组相互关联的 Skill、Command、Agent、参考资料和验证脚本。

Marketplace 中对它的描述大致如下：

```json
{
  "name": "plugin-dev",
  "description": "Comprehensive toolkit for developing Claude Code plugins. Includes 7 expert skills covering hooks, MCP integration, commands, agents, and best practices. AI-assisted plugin creation and validation.",
  "author": {
    "name": "Anthropic",
    "email": "support@anthropic.com"
  },
  "source": "./plugins/plugin-dev",
  "category": "development",
  "homepage": "https://github.com/anthropics/claude-plugins-public/tree/main/plugins/plugin-dev"
}
```

这条 Marketplace Entry 向 Claude Code 提供了几项关键信息：

```text
Plugin 名称：
plugin-dev

所属分类：
development

Plugin 来源：
当前 Marketplace 仓库中的 ./plugins/plugin-dev

维护者：
Anthropic
```

选择 `plugin-dev` 作为案例，主要有三个原因。

## 1. 它的组件结构比较完整

`plugin-dev` 包含：

```text
7 个 Skills
1 个 Command
3 个 Agents
1 个 Plugin Manifest
多组 References、Examples 和 Scripts
```

通过它，可以同时观察 Claude Code 中 Skill、Command 和 Subagent 的组织方式。

## 2. 它本身就是一套 Plugin 开发规范

它所提供的七个 Skill 覆盖：

```text
Plugin 目录结构
Skill 开发
Command 开发
Agent 开发
Hook 开发
MCP 集成
Plugin Settings
```

因此，它既是一个可以实际安装和使用的 Plugin，也是一份以 Skill 形式组织的 Claude Code Plugin 开发指南。

## 3. 它能帮助区分“开发知识”和“运行时能力”

`plugin-dev` 中包含：

```text
hook-development Skill
mcp-integration Skill
```

但这不代表它自己注册了 Hook 或启动了 MCP Server。

必须区分：

```text
教 Claude 如何开发 Hook
≠
Plugin 自身注册了 Hook

教 Claude 如何配置 MCP
≠
Plugin 自身启动了 MCP Server
```

这是理解 Claude Code Plugin 能力边界的关键。

# 二、从 Marketplace Entry 到本地 Plugin

在分析 Skill 和 Agent 之前，需要先看清 `plugin-dev` 是如何从 Marketplace 中的一条记录，变成 Claude Code 本地可以加载的 Plugin。

## 1. `marketplace.json` 中的 Plugin Entry

`plugin-dev` 首先存在于官方 Marketplace 的：

```text
claude-plugins-official/
└── .claude-plugin/
    └── marketplace.json
```

其中的 Plugin Entry 类似：

```json
{
  "name": "plugin-dev",
  "description": "Comprehensive toolkit for developing Claude Code plugins. Includes 7 expert skills covering hooks, MCP integration, commands, agents, and best practices. AI-assisted plugin creation and validation.",
  "author": {
    "name": "Anthropic",
    "email": "support@anthropic.com"
  },
  "source": "./plugins/plugin-dev",
  "category": "development",
  "homepage": "https://github.com/anthropics/claude-plugins-public/tree/main/plugins/plugin-dev"
}
```

这一层主要用于：

```text
Marketplace 浏览
Plugin 搜索
安装前信息展示
Plugin Source 定位
分类和作者识别
```

可以将它理解为：

```text
Marketplace Entry
    =
安装前 Catalog Metadata
```

这里并没有详细列出：

```text
Plugin 中有多少 Skill
有哪些 Command
有哪些 Agent
是否包含 Hook 或 MCP
每个组件具体放在哪里
```

因为 Marketplace 的主要职责是“发现和定位”，不是完整描述 Plugin 内部结构。

---

## 2. Marketplace 如何定位 Plugin Source

`plugin-dev` 的 Source 是：

```json
{
  "source": "./plugins/plugin-dev"
}
```

它表示 Plugin 位于 Marketplace 仓库的相对目录中：

```text
claude-plugins-official/
├── .claude-plugin/
│   └── marketplace.json
└── plugins/
    └── plugin-dev/
```

安装时，Claude Code 会沿着这条路径完成定位：

```text
读取 marketplace.json
    ↓
找到 plugin-dev Entry
    ↓
解析 source = ./plugins/plugin-dev
    ↓
定位 Plugin Source
    ↓
复制 Plugin 目录
    ↓
写入本地版本化 Cache
```

最终运行时使用的目录大致是：

```text
~/.claude/plugins/cache/
└── claude-plugins-official/
    └── plugin-dev/
        └── <resolved-version>/
```

因此：

```text
Marketplace Entry
    → 指向 Plugin 的原始 Source

Plugin Cache
    → 保存 Harness 实际加载的 Plugin 副本
```

Claude Code 不会一直依赖 Marketplace 原始目录运行 Plugin，而是通过本地版本化缓存实现运行隔离和版本管理。

## 4. `plugin.json`：一个很薄的 Manifest

`plugin-dev` 的 Manifest 位于：

```text
plugin-dev/
└── .claude-plugin/
    └── plugin.json
```

它的内容非常简单：

```json
{
  "name": "plugin-dev",
  "description": "Plugin development toolkit with skills for creating agents, commands, hooks, MCP integrations, and comprehensive plugin structure guidance",
  "author": {
    "name": "Anthropic",
    "email": "support@anthropic.com"
  }
}
```

它主要声明：

```text
Plugin 名称
Plugin 描述
Plugin 作者
```

更值得注意的是，它没有显式声明：

```text
Skills 列表
Commands 列表
Agents 列表
Hooks 路径
MCP Server
LSP Server
组件依赖
工具权限
```

也就是说，`plugin-dev` 并不依赖下面这种显式注册方式：

```json
{
  "skills": [
    "./skills/plugin-structure",
    "./skills/hook-development"
  ],
  "commands": [
    "./commands/create-plugin.md"
  ],
  "agents": [
    "./agents/plugin-validator.md"
  ]
}
```

它依靠 Claude Code 的标准目录自动发现机制：

```text
commands/
agents/
skills/
hooks/hooks.json
.mcp.json
.lsp.json
```

只有使用非标准目录时，才需要在 `plugin.json` 中额外提供自定义路径。

因此，`plugin.json` 的核心职责是：

```text
声明 Plugin 身份
提供基础元数据
作为本地 Plugin 的识别入口
```

真正的组件注册依赖：

```text
Convention over Configuration
约定优于配置
```

---

## 5. Marketplace Entry 与 Plugin Manifest 的关系

现在可以把两个文件放在一起理解。

### `marketplace.json`

```text
负责：
Plugin 在哪里
安装前如何展示
属于什么分类
从哪个 Source 获取
```

### `plugin.json`

```text
负责：
当前目录是什么 Plugin
本地加载时如何识别 Plugin 身份
```

可以概括为：

```text
marketplace.json
    → 外部索引

plugin.json
    → 包内身份
```

二者共同构成：

```text
Catalog Identity
+
Package Identity
```

Marketplace Entry 服务于“安装前”，Plugin Manifest 服务于“安装后”。

# 三、Plugin 内部组件完整拆解

`plugin-dev` 中真正承载能力的，不是 `plugin.json` 本身，而是标准目录中的 Skill、Command、Agent，以及附属的 References、Examples 和 Scripts。

## 1. Skills：知识与方法层

`plugin-dev` 的主体是七个 Skills：

```text
skills/
├── agent-development/
├── command-development/
├── hook-development/
├── mcp-integration/
├── plugin-settings/
├── plugin-structure/
└── skill-development/
```

每个 Skill 都位于：

```text
skills/<skill-name>/SKILL.md
```

Skill 主要负责：

```text
描述适用场景
提供领域知识
规定执行步骤
提供最佳实践
指导工具组合
说明验证方式
提供错误排查方法
```

它不是一个底层工具，而是一种面向 Agent 的程序性知识包。

---

## 2. 以 `plugin-structure` 为例

其中最基础的 Skill 是：

```text
skills/plugin-structure/SKILL.md
```

其 Frontmatter 类似：

```yaml
---
name: Plugin Structure
description: This skill should be used when the user asks to "create a plugin", "scaffold a plugin", "understand plugin structure", "organize plugin components", "set up plugin.json", "use ${CLAUDE_PLUGIN_ROOT}", "add commands/agents/skills/hooks", "configure auto-discovery", or needs guidance on plugin directory layout, manifest configuration, component organization, file naming conventions, or Claude Code plugin architecture best practices.
version: 0.1.0
---
```

这里有三个关键字段。

### `name`

```yaml
name: Plugin Structure
```

这是 Skill 的显示名称或逻辑身份。

其目录名是：

```text
plugin-structure
```

放在 Plugin 中后，运行时通常会带上 Plugin 命名空间：

```text
plugin-dev:plugin-structure
```

### `description`

`description` 不只是普通介绍，它还承担 Skill 路由信息。

其中主动列出了大量典型任务：

```text
create a plugin
scaffold a plugin
plugin structure
plugin.json
auto-discovery
component organization
```

其目的，是帮助 Claude 判断：

> 当前用户的请求是否适合加载这个 Skill？

因此，Skill 触发大致依赖：

```text
用户请求
    ↓
与 Skill Description 进行语义匹配
    ↓
模型判断是否需要该 Skill
    ↓
加载 SKILL.md
```

### `version`

Skill 还声明了自己的版本：

```yaml
version: 0.1.0
```

这里需要区分：

```text
Plugin Version
    → 整个能力包的版本

Skill Version
    → 单个 Skill 内容的版本
```

但 Marketplace 安装、Plugin Cache 和整体更新，仍然主要围绕 Plugin 进行，而不是独立安装某个 Skill 版本。

---

## 3. Skill 正文负责什么

`plugin-structure` 的正文会进一步说明：

```text
Plugin 标准目录
plugin.json 字段
自定义组件路径
Command 目录
Agent 目录
Skill 目录
Hook 配置
MCP 配置
${CLAUDE_PLUGIN_ROOT}
命名规范
自动发现流程
最佳实践
常见错误
```

这些内容并不会直接增加新的系统工具，而是向 Claude 提供：

```text
领域知识
结构约束
执行流程
配置示例
验证方法
故障排查经验
```

所以，Skill 更准确的定义是：

> 告诉 Agent 某类任务应该怎样完成的程序性知识包。

---

## 4. Skill 的渐进式加载

`plugin-dev` 的 Skill 并不是在 Claude Code 启动时全部加载。

它采用的是渐进式披露：

```text
第一层：Metadata
    → name + description
    → 用于 Skill 发现和匹配

第二层：SKILL.md
    → Skill 被触发后加载
    → 提供核心方法和工作流

第三层：References / Examples / Scripts
    → 确有需要时再读取或运行
```

完整流程可以表示为：

```text
Skill Catalog
    ↓
任务语义匹配
    ↓
加载核心 SKILL.md
    ↓
按需读取 References
    ↓
按需读取 Examples
    ↓
按需运行 Scripts
```

如果七个 Skill 及其全部参考资料都在会话启动时加载，容易造成：

```text
Token 消耗过高
无关内容进入上下文
模型注意力分散
Prompt Cache 更容易失效
```

渐进式加载的核心目的，就是让 Skill 数量可以扩大，而不必线性增加初始上下文成本。

---

## 5. References、Examples 与 Scripts

成熟的 Skill 并不只有一个 `SKILL.md`。

例如：

```text
hook-development/
├── SKILL.md
├── examples/
├── references/
└── scripts/
```

这些附属目录承担不同职责。

### References

```text
references/
```

通常保存：

```text
详细规范
API 说明
设计模式
安全约束
高级用法
迁移指南
```

它们是深层知识，不需要每次都加载。

### Examples

```text
examples/
```

通常保存：

```text
可复制的 Hook 示例
MCP 配置示例
Command 示例
Agent 示例
Plugin 目录模板
```

相比单纯的自然语言说明，示例能给 Claude 提供更明确的结构和实现方式。

### Scripts

```text
scripts/
```

通常用于：

```text
Schema 校验
Frontmatter 解析
文件生成
静态检查
Hook 测试
结构验证
```

这说明一个成熟 Skill 的结构不是：

```text
Prompt
```

而更接近：

```text
Instructions
+
References
+
Examples
+
Deterministic Utilities
```

其中 Markdown 负责指导模型，脚本负责补充确定性。

---

## 6. Command：显式工作流入口

`plugin-dev` 只提供了一个 Command：

```text
commands/
└── create-plugin.md
```

安装后，用户可以通过：

```text
/plugin-dev:create-plugin
```

显式启动 Plugin 创建流程。

这个 Command 描述了一个从零创建 Claude Code Plugin 的端到端工作流，大致包括：

```text
1. Discovery
2. Component Planning
3. Detailed Design
4. Structure Creation
5. Component Implementation
6. Validation
7. Testing
8. Documentation
```

Command 和 Skill 虽然都使用 Markdown，但职责不同。

```text
Command
    → 用户显式触发
    → 启动一次具体工作流

Skill
    → Claude 按任务语义选择
    → 提供某个步骤所需的专业方法
```

例如：

```text
用户执行：
/plugin-dev:create-plugin
    ↓
进入 Plugin 创建工作流
    ↓
需要规划目录
    → 加载 plugin-structure Skill
    ↓
需要创建 Agent
    → 加载 agent-development Skill
    ↓
需要创建 Hook
    → 加载 hook-development Skill
```

可以概括为：

```text
Command
    → 决定从哪里开始

Skill
    → 决定某个步骤应该怎样完成
```

---

## 7. `create-plugin` 更像 Workflow Prompt

`create-plugin` 并不是一个简单的一次性提示词。

它会指导 Claude：

```text
理解需求
规划所需组件
选择相关 Skills
调用 Agent 创建或验证组件
运行验证脚本
生成文档
```

完整链路可以抽象为：

```text
/plugin-dev:create-plugin
    ↓
需求发现
    ↓
组件规划
    ├── 是否需要 Skill
    ├── 是否需要 Command
    ├── 是否需要 Agent
    ├── 是否需要 Hook
    └── 是否需要 MCP
    ↓
加载对应开发 Skill
    ↓
委托专用 Agent
    ↓
生成目录和文件
    ↓
执行验证
    ↓
生成 README
```

它接近一个：

```text
Workflow Prompt
```

但仍然不是一个完全确定性的 Workflow Engine。

例如：

```text
具体加载哪些 Skill
是否调用某个 Agent
每一步执行多少轮
验证失败后如何重试
```

仍然由 Claude 的 Agent Loop 决定。

---

## 8. Agents：独立执行与验证层

`plugin-dev` 提供了三个 Agents：

```text
agents/
├── agent-creator.md
├── plugin-validator.md
└── skill-reviewer.md
```

它们分别负责不同的执行任务。

### `agent-creator`

主要用于：

```text
创建新的 Subagent 定义
设计 Agent Frontmatter
生成 Agent System Prompt
优化 Agent Description
检查 Agent 工具范围
```

它是一个“生成 Agent 的 Agent”。

### `plugin-validator`

主要用于：

```text
检查 Plugin 目录
验证 plugin.json
检查组件位置
检查缺失文件
识别路径错误
验证整体 Plugin 结构
```

它承担 Plugin 级验证。

### `skill-reviewer`

主要用于：

```text
审查 SKILL.md
检查 Description 是否容易触发
检查内容是否过长
检查渐进式披露
检查 References 与 Scripts 的组织
```

它承担 Skill 级质量审查。

---

## 9. 为什么要使用独立 Agent

这些任务理论上都可以由主 Claude 完成。

但拆成独立 Agent 有几个优势：

```text
拥有独立上下文
角色更加聚焦
System Prompt 更明确
可以限制可用工具
可以控制模型和最大轮次
减少主上下文污染
```

Plugin 中的 Agent 定义位于：

```text
agents/*.md
```

Plugin 启用后，它们会以带 Plugin 命名空间的形式出现，例如：

```text
plugin-dev:plugin-validator
```

可以由主 Claude 自动委托，也可以被用户显式选择。

---

## 10. Agent 与 Skill 的边界

以 `skill-development` 和 `skill-reviewer` 为例。

### Skill

```text
skill-development
```

主要提供：

```text
怎样编写 Skill
Skill 标准目录
Description 如何设计
References 如何组织
渐进式披露原则
```

它负责提供规范和方法。

### Agent

```text
skill-reviewer
```

主要执行：

```text
读取一个具体的 SKILL.md
按照规范进行检查
输出审查结果
给出修改建议
```

它负责实际完成任务。

因此：

```text
Skill
    → 知道应该怎样做

Agent
    → 在独立上下文中真正去做
```

两者组合后形成：

```text
skill-development
    → 提供规则

skill-reviewer
    → 根据规则检查具体产物
```

---

## 11. Plugin Agent 的权限边界

Plugin Agent 可以声明一些运行参数，例如：

```text
model
effort
maxTurns
tools
disallowedTools
skills
memory
background
isolation
```

但出于安全考虑，Plugin 携带的 Agent 不能自行控制部分高风险能力，例如：

```text
hooks
mcpServers
permissionMode
```

否则，第三方 Plugin 就可能通过某个 Agent 定义，静默完成：

```text
挂载额外 MCP
改变权限模式
注册隐蔽 Hook
```

因此，Claude Code 将高风险运行时扩展保留在 Plugin 根级配置和 Harness 权限层，而不是允许每个 Agent 独立修改。

---

## 12. Plugin 没有注册的运行时组件

`plugin-dev` 中有 Hook 和 MCP 的开发 Skill，但它自身并没有注册 Hook、MCP Server 或 LSP Server。

### 没有直接注册 Hook

它有：

```text
skills/hook-development/
```

但没有：

```text
hooks/
└── hooks.json
```

也没有在 `plugin.json` 中配置 Hook。

因此：

```text
hook-development Skill
    → 教 Claude 如何开发 Hook

plugin-dev Plugin
    → 自身没有启用 Hook
```

安装它之后，不会自动：

```text
拦截 Write
拦截 Bash
监听 SessionStart
执行格式化脚本
```

### 没有直接注册 MCP Server

它有：

```text
skills/mcp-integration/
```

但没有：

```text
.mcp.json
```

也没有在 `plugin.json` 中声明 MCP Server。

因此：

```text
mcp-integration Skill
    → 是 MCP 开发知识

.mcp.json
    → 才是 MCP Server 注册配置
```

### 没有注册 LSP Server

它也没有：

```text
.lsp.json
```

因此不会向 Claude Code 注册：

```text
语法诊断
定义跳转
引用查找
类型信息
```

### 组件能力表

| 组件            | 是否包含 | Harness 中的作用 |
| ------------- | ---: | ------------ |
| `plugin.json` |    是 | 声明 Plugin 身份 |
| `skills/`     |    是 | 增加程序性知识      |
| `commands/`   |    是 | 增加显式工作流入口    |
| `agents/`     |    是 | 增加独立执行角色     |
| `hooks/`      |    否 | 不注册生命周期事件    |
| `.mcp.json`   |    否 | 不增加 MCP Tool |
| `.lsp.json`   |    否 | 不增加语言服务器     |

这说明研究一个 Plugin 时，不能只看它“谈到了什么”，而要看它“实际注册了什么”。

# 四、Plugin 各组件如何协同工作

单独看每个目录，只能知道 Plugin 中有什么；继续观察组件关系，才能理解它是如何完成复杂任务的。

## 1. 三层能力模型

`plugin-dev` 可以抽象成三层：

```text
第一层：Command
    → 提供总体工作流入口

第二层：Skills
    → 提供不同领域的方法和知识

第三层：Agents
    → 提供独立执行和验证角色
```

此外还有一层辅助资源：

```text
References / Examples / Scripts
    → 提供详细规范、实现样例和确定性工具
```

整体模型是：

```text
用户启动任务
    ↓
Command 建立总体流程
    ↓
Skill 提供专业方法
    ↓
Agent 执行子任务
    ↓
Script 做确定性验证
    ↓
返回最终结果
```

---

## 2. `create-plugin` 的完整协作链

假设用户执行：

```text
/plugin-dev:create-plugin
```

其潜在执行链大致如下：

```text
/plugin-dev:create-plugin
    ↓
分析 Plugin 需求
    ↓
规划所需组件
    ↓
加载 plugin-structure
    ↓
确定目录和 Manifest
    ↓
根据需要加载：
    ├── skill-development
    ├── command-development
    ├── agent-development
    ├── hook-development
    ├── mcp-integration
    └── plugin-settings
    ↓
委托专用 Agent
    ├── agent-creator
    ├── skill-reviewer
    └── plugin-validator
    ↓
读取 Examples / References
    ↓
执行验证 Scripts
    ↓
生成完整 Plugin
```

---

## 3. 典型组件组合

不同任务会调用不同的 Skill 和 Agent。

```text
需要设计 Plugin 目录
    → plugin-structure Skill

需要创建新的 Skill
    → skill-development Skill
    → skill-reviewer Agent

需要创建 Subagent
    → agent-development Skill
    → agent-creator Agent

需要验证整个 Plugin
    → plugin-structure Skill
    → plugin-validator Agent

需要创建 Hook
    → hook-development Skill
    → Hook 示例与验证脚本

需要配置 MCP
    → mcp-integration Skill
    → MCP 配置示例
```

这种组合方式体现了：

```text
Command 负责整体任务
Skill 负责专业方法
Agent 负责实际执行
Script 负责确定性检查
```

---

## 4. 组件依赖主要存在于自然语言中

需要注意，`plugin-dev` 的组件关系并不是一个结构化依赖图。

它通常不会声明：

```json
{
  "dependsOn": [
    "plugin-structure",
    "plugin-validator"
  ]
}
```

更多时候，组件关系存在于 Markdown 指令中：

```text
Command 正文要求使用某个 Skill
Skill 正文建议委托某个 Agent
Agent 读取 Plugin 内的 References
Skill 指示运行某个 Script
```

所以 Claude Code Plugin 的编排依赖：

```text
自然语言指令
+
组件命名约定
+
Harness 自动发现
+
模型自主判断
```

而不是一个完全声明式的 DAG。

这赋予了 Plugin 很高的灵活性，但也带来了一些可靠性问题：

```text
组件是否调用依赖模型判断
执行顺序未必完全固定
依赖关系难以静态分析
调用链不够容易观测
```

---

## 5. `${CLAUDE_PLUGIN_ROOT}` 解决资源定位

Plugin 安装后的实际路径可能包含 Marketplace、Plugin 名和版本：

```text
~/.claude/plugins/cache/
└── claude-plugins-official/
    └── plugin-dev/
        └── <version>/
```

因此，Skill、Command、Agent 和 Hook 不应该硬编码：

```text
/Users/xxx/.claude/plugins/cache/...
```

Claude Code 提供：

```text
${CLAUDE_PLUGIN_ROOT}
```

用于在运行时指向当前 Plugin 根目录。

例如：

```text
${CLAUDE_PLUGIN_ROOT}/skills/hook-development/scripts/test-hook.sh
```

其作用是：

```text
Plugin 中的逻辑路径
    ↓
Harness 运行时解析
    ↓
当前版本实际 Cache 路径
```

这样，Plugin 即使被安装到不同机器、不同 Marketplace 或不同版本目录，内部资源引用仍然有效。

# 五、Harness 最终如何加载和暴露能力

现在可以进入最关键的一层：这些目录和 Markdown 文件，如何变成 Claude Code Harness 中的真实能力。

## 1. Plugin 启用后的扫描流程

当 `plugin-dev` 被安装并启用后，Harness 大致执行：

```text
读取 enabledPlugins
    ↓
定位 plugin-dev 的 Cache 目录
    ↓
读取 .claude-plugin/plugin.json
    ↓
确认 Plugin 身份
    ↓
扫描标准组件目录
    ↓
注册运行时能力
```

标准扫描对象包括：

```text
commands/
    → 查找 Command Markdown

agents/
    → 查找 Agent 定义

skills/
    → 查找包含 SKILL.md 的目录

hooks/hooks.json
    → 如果存在则注册 Hook

.mcp.json
    → 如果存在则启动 MCP Server

.lsp.json
    → 如果存在则启动 LSP Server
```

`plugin-dev` 中不存在 Hook、MCP 和 LSP 配置，因此这些阶段会被跳过。

---

## 2. Harness 最终注册的能力

启用 `plugin-dev` 后，Claude Code 最终可以获得：

### 一个 Plugin 身份

```text
plugin-dev
```

用于：

```text
命名空间
启停管理
版本追踪
Marketplace 来源识别
```

### 七个 Skills

```text
plugin-dev:agent-development
plugin-dev:command-development
plugin-dev:hook-development
plugin-dev:mcp-integration
plugin-dev:plugin-settings
plugin-dev:plugin-structure
plugin-dev:skill-development
```

### 一个 Slash Command

```text
/plugin-dev:create-plugin
```

### 三个 Subagents

```text
plugin-dev:agent-creator
plugin-dev:plugin-validator
plugin-dev:skill-reviewer
```

### 若干内部资源

```text
References
Examples
Validation Scripts
Templates
```

这些资源不会直接成为顶级入口，但会被 Skill、Command 和 Agent 按需读取或执行。

---

## 3. Harness 没有注册的能力

由于对应配置不存在，Harness 不会注册：

```text
Plugin Hooks
MCP Servers
LSP Servers
Background Monitors
```

所以 `plugin-dev` 的运行时能力表更准确地是：

```text
Plugins：1
Skills：7
Commands：1
Agents：3
Hooks：0
MCP Servers：0
LSP Servers：0
```

这进一步说明：

```text
Plugin 描述中提到某类能力
≠
Plugin 已经向 Harness 注册该能力
```

---

## 4. 用户请求如何触发不同能力

### 场景一：自动匹配 Skill

用户提问：

```text
Claude Code Plugin 的标准目录是什么？
```

Harness 可能执行：

```text
读取可用 Skill Metadata
    ↓
匹配 plugin-structure 的 Description
    ↓
加载 plugin-structure/SKILL.md
    ↓
根据需要读取 References
    ↓
生成回答
```

### 场景二：显式调用 Command

用户执行：

```text
/plugin-dev:create-plugin 数据库迁移插件
```

Harness 可能执行：

```text
加载 create-plugin Command
    ↓
分析需求
    ↓
调用 plugin-structure Skill
    ↓
调用 mcp-integration Skill
    ↓
委托 agent-creator
    ↓
委托 plugin-validator
    ↓
生成 Plugin
```

### 场景三：委托 Agent

用户提出：

```text
检查这个 SKILL.md 是否符合 Claude Code 规范。
```

Harness 可能执行：

```text
加载 skill-development Skill
    ↓
委托 skill-reviewer Agent
    ↓
Agent 在独立上下文中读取目标文件
    ↓
输出审查结果
```

---

## 5. 不同组件的确定性层级

Skill、Command、Agent 和 Script 的执行确定性并不相同。

```text
Skill 自动匹配
    → 是否触发高度依赖模型判断

Command 显式调用
    → 入口确定，但内部流程仍由模型执行

Agent 显式委托
    → 执行角色确定，但内部步骤仍由模型决定

Script
    → 输入确定后，执行行为更接近传统程序

Hook
    → 由生命周期事件触发，确定性最高
```

可以概括为：

```text
模型驱动能力
Skill → Command → Agent

程序驱动能力
Script → Hook
```

当然，这并不是绝对排序，但能够帮助理解各组件的职责差异。

# 六、从 `plugin-dev` 看 Claude Code Plugin 的设计

通过完整拆解，可以总结出 Claude Code Plugin 的几个核心设计特点。

## 1. 薄 Manifest，厚目录

`plugin.json` 本身非常精简：

```text
name
description
author
```

真正的能力分布在：

```text
skills/
commands/
agents/
references/
examples/
scripts/
```

这是一种典型的：

```text
Thin Manifest
+
Rich Package Layout
```

---

## 2. Plugin 是能力集合，不是单一 Prompt

`plugin-dev` 包含：

```text
7 Skills
1 Command
3 Agents
多组参考资料和脚本
```

它不是一个单一功能，而是一套面向 Plugin 开发领域的能力组合。

因此：

```text
Plugin
≠
Prompt

Plugin
=
Capability Package
```

---

## 3. 约定优于配置

Plugin 作者不需要在 Manifest 中逐个注册所有组件。

只要遵循：

```text
skills/
commands/
agents/
hooks/hooks.json
.mcp.json
.lsp.json
```

Harness 就可以自动发现。

这种方式降低了 Plugin 的开发成本，也让目录本身具备可读性。

---

## 4. Skill 是主要知识载体

Claude Code 将大量领域知识放在：

```text
skills/<name>/SKILL.md
```

以及：

```text
references/
examples/
scripts/
```

Skill 不只是短 Prompt，而是一个可渐进加载的知识和流程包。

---

## 5. Command 提供显式入口，Agent 提供上下文隔离

```text
Command
    → 让用户明确启动一个任务

Agent
    → 将具体任务放入独立上下文执行
```

这两种机制分别解决：

```text
任务入口
上下文隔离
```

---

## 6. 教授能力与注册能力分离

`plugin-dev` 最值得注意的一点是：

```text
hook-development Skill
≠ Hook Runtime

mcp-integration Skill
≠ MCP Server
```

一个 Plugin 可以教授 Claude 如何开发某类能力，但不一定自己注册该能力。

---

## 7. 模型是组件编排器

Claude Code 并没有要求 Plugin 提供一个完整声明式工作流。

大多数时候，组件由模型动态组合：

```text
选择 Skill
委托 Agent
读取 References
执行 Scripts
```

因此，Plugin 的灵活性很高，但可靠性也在一定程度上依赖模型。

---

## 8. 这套设计的优势

### 扩展简单

新增一个 Skill，只需要增加：

```text
skills/new-skill/SKILL.md
```

### 内容可组合

Command、Skill、Agent 和 Script 可以围绕同一任务组合。

### 上下文成本可控

通过渐进式加载，不必在启动时加载所有内容。

### Git 友好

绝大多数能力都由 Markdown、JSON 和脚本文件组成。

### 适合人工审查

Plugin 的核心内容可以直接阅读，不依赖二进制包。

---

## 9. 这套设计的局限

### 组件依赖不够结构化

缺少类似：

```text
Command A depends on Skill B
Skill B may invoke Agent C
```

的显式依赖声明。

### Skill 路由依赖模型

Description 质量会直接影响：

```text
是否触发
是否误触发
是否与其他 Skill 冲突
```

### Command 不是确定性 DAG

Command 中定义的阶段仍然是 Prompt 指令，而不是 Harness 强制执行的状态机。

### 输入输出缺少统一 Schema

Skill、Command 和 Agent 之间通常通过自然语言传递结果。

### 验证能力依赖作者主动补充

并不是每个 Plugin 都会提供：

```text
Validator Agent
Validation Scripts
Examples
Reference Docs
```

---

## 10. 对自研 Harness 的启发

Claude Code 的以下设计值得保留：

```text
标准目录自动发现
Plugin 统一命名空间
Skill 渐进式加载
Command 显式入口
Subagent 上下文隔离
${PLUGIN_ROOT} 路径抽象
```

但企业级 Harness 可以进一步增加结构化声明。

例如：

```yaml
name: create-plugin
type: workflow

requires:
  skills:
    - plugin-structure
    - skill-development

mayDelegate:
  agents:
    - agent-creator
    - plugin-validator

inputs:
  type: object
  properties:
    description:
      type: string

outputs:
  type: object
  properties:
    pluginPath:
      type: string
    validation:
      type: object
```

这样可以补充 Claude Code 当前相对薄弱的：

```text
组件依赖声明
输入输出 Schema
执行链可观测性
工作流验证
静态权限分析
```

# 总结

通过 `plugin-dev` 可以看到，一个真实的 Claude Code Plugin，并不一定需要同时包含所有类型的扩展组件。

它可以根据自己的目标，选择合适的能力组合。

`plugin-dev` 的实际组成是：

```text
Plugin Manifest
    → 声明 Plugin 身份

7 Skills
    → 提供 Plugin 开发知识和方法

1 Command
    → 提供完整 Plugin 创建入口

3 Agents
    → 提供生成、审查和验证角色

References / Examples / Scripts
    → 提供深层知识、样例和确定性工具
```

它没有直接携带：

```text
Hook
MCP Server
LSP Server
```

但提供了开发这些组件的 Skill。

因此，理解 Claude Code Plugin 时必须区分：

```text
Plugin 包含某类开发知识
和
Plugin 实际向 Harness 注册某类运行时能力
```

从 Harness 角度看，`plugin-dev` 最终真正暴露的是：

```text
7 个可自动或显式加载的 Skills
1 个显式 Slash Command
3 个可委托的 Subagents
0 个 Hooks
0 个 MCP Servers
0 个 LSP Servers
```

整个链路可以概括为：

```text
Marketplace Entry
    ↓
定位 Plugin Source
    ↓
复制到版本化 Cache
    ↓
读取 plugin.json
    ↓
扫描标准目录
    ↓
注册 Skill / Command / Agent
    ↓
模型根据任务组合能力
    ↓
读取 References 或执行 Scripts
    ↓
完成最终任务
```

这说明 Claude Code Plugin 的核心并不是复杂的 Manifest，而是：

```text
标准目录
+
自动发现
+
Markdown 能力定义
+
渐进式上下文加载
+
模型驱动的组件编排
```
