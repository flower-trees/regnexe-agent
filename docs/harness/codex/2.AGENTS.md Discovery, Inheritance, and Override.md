# Harness Marketplace 剖析系列 - 之 Codex：AGENTS.md 的发现、继承与覆盖

上一篇中，我们已经建立了 Codex 扩展体系的整体静态地图：

```
AGENTS.md
→ 持续生效的项目指导

config.toml
→ Harness 运行配置

Skills
→ 可复用任务流程

Custom Agents
→ 专门执行角色

MCP
→ 外部工具与系统

Hooks
→ 生命周期扩展

requirements.toml
→ 企业级强制约束

```

在这些能力中，AGENTS.md 是最基础、也最容易被低估的一层。

很多人第一次使用时，会把它理解成：

```
给 Codex 看的 README

```

或者：

```
一个长期 Prompt 文件

```

这种理解只触及了表面。

更准确地说，AGENTS.md 是 Codex 在真正开始任务前，用来构建项目级持久指令链的公开接口。

它解决的不是某一次具体任务，而是：

```
这个项目使用什么技术栈？
代码应该遵循哪些约定？
修改后需要运行什么测试？
哪些目录应该优先阅读？
哪些操作必须先询问？
不同模块是否有不同规则？

```

如果没有 AGENTS.md，这些要求往往只能反复写进每一次用户 Prompt。

例如：

```
请使用 Java 21。
不要在 Controller 中直接访问 Repository。
修改后运行 Maven 测试。
不要随意添加新的依赖。

```

当规则越来越多，用户就会面临两个问题：

```
每次都要重复输入
↓
容易遗漏

不同开发者写法不同
↓
Agent 行为不一致

```

AGENTS.md 的作用，就是把这些长期规则从单次 Prompt 中抽离出来，变成可提交到代码仓库、可按目录继承、可由团队共同维护的持久指导。

完整过程可以概括为：

```
Codex 启动
↓
识别全局指导
↓
识别项目根
↓
从项目根走到当前目录
↓
逐级选择 AGENTS 文件
↓
按照目录顺序拼接
↓
形成 Instruction Chain
↓
注入当前 Session
↓
Agent 开始执行用户任务

```

本文重点回答：

```
全局 AGENTS.md 在哪里？
AGENTS.override.md 如何生效？
Codex 如何识别项目根？
为什么从项目根走向当前目录？
同一个目录中多个文件如何选择？
多个目录的内容怎样合并？
所谓"靠近当前目录的规则覆盖上层规则"到底是什么意思？
32 KiB 限制如何计算？
fallback 文件名有什么作用？
AGENTS.md 与用户 Prompt、Skill、config.toml 如何分工？
Subagent 是否继承 AGENTS.md？
CLI、IDE、App、Cloud 的行为是否完全一致？

```

# 一、AGENTS.md 位于 Codex 指令体系的哪一层

在 Codex 中，模型最终看到的指令并不只来自用户输入。

可以先抽象成：

```
平台与系统指令
↓
Harness Developer Instructions
↓
AGENTS.md 指令链
↓
Skill 或 Agent 专属指令
↓
当前用户 Prompt
↓
工具返回结果

```

这里并不代表公开的内部 Message 数组结构，而是一种工程化分层。

AGENTS.md 的特点是：

```
由用户或项目维护
持续作用于当前 Session
通常在 Agent 开始工作前加载
可以随代码仓库共同分发
可以根据目录结构进行局部细化

```

OpenAI 对 Codex 定制体系的定义也明确区分了这些组件：

```
AGENTS.md
→ 持久的项目指导

Skills
→ 可复用工作流和领域知识

MCP
→ 外部系统能力

Subagents
→ 专门执行者

```

这些能力是互补关系，而不是互相替代。AGENTS.md 主要塑造 Agent 在仓库中的长期行为，并应尽量保持精简。

因此：

```
AGENTS.md
≠
普通项目文档

AGENTS.md
≠
某一次任务 Prompt

AGENTS.md
≠
可执行工作流

AGENTS.md
=
持续生效的项目行为约束

```

# 二、全局 AGENTS.md 如何加载

Codex 首先处理的是全局指导。

默认位置是：

```
~/.codex/AGENTS.md

```

如果用户通过：

```
CODEX_HOME

```

修改了 Codex 主目录，则全局指导文件也会跟随 CODEX_HOME。

例如：

```bash
export CODEX_HOME=/data/codex-home

```

对应文件变为：

```
/data/codex-home/AGENTS.md

```

全局文件适合保存个人长期偏好：

```
默认沟通语言
代码审查风格
修改后是否运行测试
常用包管理器
是否主动生成文档
是否允许添加依赖
希望输出简洁还是详细

```

例如：

```markdown

# Global working agreements

- 默认使用中文说明。
- 修改代码前先简要说明计划。
- 修改后运行与变更相关的测试。
- 不要在未说明理由的情况下引入新依赖。
- 进行代码审查时，优先指出正确性、安全性和并发问题。

```

它的作用范围是：

```
当前用户启动的所有 Codex 项目

```

因此，全局文件应该保存个人长期习惯，而不应写入某个具体项目的业务规则。

# 三、AGENTS.override.md 如何生效

在全局目录中，Codex并不是同时加载：

```
AGENTS.md
+
AGENTS.override.md

```

而是按照优先顺序选择一个。

规则是：

```
如果 AGENTS.override.md 存在且非空
→ 使用 AGENTS.override.md

否则
→ 使用 AGENTS.md

```

也就是说，同一级目录中：

```
AGENTS.override.md
>
AGENTS.md

```

Codex 每个目录最多只选择一个指导文件。官方发现规则明确指出，全局层优先读取 AGENTS.override.md；只有 Override 不存在或为空时，才读取 AGENTS.md。

这意味着 Override 不是在基础文件后面追加内容。

它更接近：

```
同级完整替换

```

例如：

```
~/.codex/
├── AGENTS.md
└── AGENTS.override.md

```

其中：

```markdown

# AGENTS.md

- 修改后运行测试。
- 优先使用稳定版本依赖。
- 回复保持简洁。

```

```markdown

# AGENTS.override.md

- 当前阶段只进行只读分析。
- 不要修改任何文件。
- 不要运行可能产生副作用的命令。

```

本次启动中生效的是：

```
AGENTS.override.md

```

而不是两者合并。

## 1. Override 适合什么场景
临时切换工作方式

例如：

```
平时：
允许修改和测试

临时审计：
只读分析，不改文件

```
调试 Agent 行为

```
要求输出加载的指令来源
要求记录决策过程
要求暂停自动修改

```
本地个性化但不修改仓库规则

例如项目共享：

```
AGENTS.md

```

个人本地增加一个被 .gitignore 忽略的：

```
AGENTS.override.md

```

用来改变当前工作方式。

## 2. Override 为什么不是 Merge

如果 Override 仍然与基础文件合并，就可能出现冲突：

```
AGENTS.md：
修改完成后自动修复格式。

AGENTS.override.md：
只读分析，不允许修改文件。

```

如果两者同时加载，Agent 需要自行判断谁优先。

使用同级替换，可以建立更明确的逻辑：

```
基础文件
→ 默认指导

Override
→ 当前目录的替代指导

```

# 四、Codex 如何识别项目根

处理完全局指导后，Codex 需要找到当前项目的根目录。

通常情况下，它会把 Git 根目录视为项目根。

例如当前目录是：

```
/workspace/shop/services/payment/src/main/java

```

仓库结构是：

```
/workspace/shop/
├── .git/
├── AGENTS.md
└── services/
└── payment/
└── src/
└── main/
└── java/

```

Codex 会从当前目录向上寻找项目根标识，识别：

```
/workspace/shop

```

为项目根。

随后，AGENTS 发现方向会反过来：

```
项目根
↓
当前工作目录

```

即：

```
/workspace/shop
/workspace/shop/services
/workspace/shop/services/payment
/workspace/shop/services/payment/src
/workspace/shop/services/payment/src/main
/workspace/shop/services/payment/src/main/java

```

Codex 的项目配置发现也使用相似的项目根逻辑。project_root_markers 可以配置哪些文件或目录标识被用来识别项目根。

## 1. 为什么不是一直扫描到文件系统根目录

假设当前目录是：

```
/Users/user/work/company/payment-service

```

如果 Codex 一直向上扫描到：

```
/

```

可能意外读取：

```
/Users/AGENTS.md
/Users/user/work/AGENTS.md

```

这些文件未必属于当前项目。

项目根提供了一个隔离边界：

```
项目根以上
→ 不属于当前 Repository 指令链

项目根到当前目录
→ 属于当前项目范围

```

## 2. 自定义 project_root_markers

并非所有项目都使用 Git。

例如：

```
大型源码快照
压缩包解压项目
内部构建系统
不含 .git 的部署目录

```

可以通过：

```toml
project_root_markers = [
".git",
"pom.xml",
"package.json",
"WORKSPACE",
"Cargo.toml"
]

```

调整项目根识别。

不过标识设计需要谨慎。

如果使用：

```toml
project_root_markers = ["package.json"]

```

在 Monorepo 中多个子项目都包含 package.json，可能导致某个子目录被识别为新的项目根，从而缩短 AGENTS 发现范围。

更稳妥的是选择：

```
真正代表 Repository 边界的文件

```

而不是任意模块配置。

## 3. 找不到项目根时怎么办

如果 Codex 无法识别项目根，官方规则是：

```
只检查当前工作目录

```

它不会无限向父目录加载项目指导。

此时假设：

```
/tmp/code/
├── AGENTS.md
└── src/
└── main/

```

用户在：

```
/tmp/code/src/main

```

启动 Codex，但没有任何项目根 Marker。

Codex 可能只检查：

```
/tmp/code/src/main

```

而不会自动加载：

```
/tmp/code/AGENTS.md

```

这种情况下应该：

```
从项目根启动 Codex
或者
配置 project_root_markers

```

# 五、项目 AGENTS.md 如何逐层发现

找到项目根后，Codex 从项目根开始，沿目录路径走向当前工作目录。

假设结构如下：

```
shop-platform/
├── AGENTS.md
│
├── services/
│ ├── AGENTS.md
│ │
│ ├── payment/
│ │ ├── AGENTS.override.md
│ │ └── src/
│ │
│ └── search/
│ └── AGENTS.md
│
└── frontend/
└── AGENTS.md

```

当前工作目录：

```
shop-platform/services/payment/src

```

Codex 检查的目录依次是：

```
shop-platform/
shop-platform/services/
shop-platform/services/payment/
shop-platform/services/payment/src/

```

不会检查：

```
shop-platform/services/search/
shop-platform/frontend/

```

因为它们不在项目根到当前目录的路径上。

最终可能加载：

```
shop-platform/AGENTS.md
shop-platform/services/AGENTS.md
shop-platform/services/payment/AGENTS.override.md

```

## 1. 每个目录的文件选择顺序

在每一个目录中，Codex 按以下顺序检查：

```
1. AGENTS.override.md
2. AGENTS.md
3. project_doc_fallback_filenames 中配置的文件

```

并且：

```
每个目录最多选择一个文件

```

官方发现流程明确规定，项目范围从项目根走到当前目录，每层优先寻找 AGENTS.override.md，其次是 AGENTS.md，最后才是 fallback 文件。

例如：

```
payment/
├── AGENTS.override.md
├── AGENTS.md
└── TEAM_GUIDE.md

```

如果三个文件均非空，生效的是：

```
AGENTS.override.md

```

另外两个在该目录中被忽略。

## 2. 为什么每个目录只选择一个

如果同一目录允许同时加载多个文件，容易出现不可预测的顺序：

```
AGENTS.md
TEAM_GUIDE.md
AI_RULES.md
LOCAL_GUIDE.md

```

Codex 需要判断：

```
谁先？
谁后？
谁覆盖谁？

```

通过"每层一个文件"，可以把结构简化为：

```
目录层级
→ 决定继承关系

文件优先级
→ 决定当前目录选哪一个

```

# 六、多个目录的内容如何合并

各目录选出指导文件后，Codex 按照：

```
项目根
↓
当前工作目录

```

的顺序连接内容，中间使用空行分隔。

假设：

根目录 AGENTS.md

```markdown

# Repository rules

- 所有代码必须通过 CI。
- 新增公共 API 必须补充文档。
- 禁止提交密钥。

```
services/AGENTS.md

```markdown

# Service rules

- 后端服务使用 Java 21。
- 使用 Maven 运行测试。
- Controller 不直接访问 Repository。

```
services/payment/AGENTS.override.md

```markdown

# Payment rules

- 支付模块必须使用 make test-payment。
- 金额计算必须使用 BigDecimal。
- 修改支付状态机前先输出影响分析。

```

最终指令链类似：

```
Repository rules
↓
Service rules
↓
Payment rules

```

组合后的内容可以理解为：

```markdown

# Repository rules
...

# Service rules
...

# Payment rules
...

```

## 1. "靠近当前目录的规则覆盖上层"是什么意思

这里的"覆盖"不是配置文件字段级覆盖。

Codex 并不会解析：

```yaml
testCommand: npm test

```

然后构建结构化 Map。

AGENTS.md 本质仍然是自然语言指令。

所谓覆盖，主要是：

```
更具体的指导出现在组合 Prompt 的后面
模型应优先遵循后出现、更贴近当前目录的规则

```

例如：

```
根目录：
修改后运行 npm test。

payment 目录：
修改支付模块时运行 make test-payment，不运行 npm test。

```

最终模型应优先使用：

```
make test-payment

```

因为它更具体，且出现在更靠后的目录指导中。

## 2. 它不是完全确定性的配置 Merge

假设上层写：

```
必须运行全部测试。

```

下层写：

```
只运行当前模块测试。

```

模型需要通过语义判断哪条更具体。

这不同于：

```toml
test_scope = "all"
test_scope = "module"

```

后者可以做确定性的字段覆盖。

因此，AGENTS 继承仍有自然语言的不确定性。

更好的写法是明确表达：

```markdown
在 payment 模块中，本目录规则替代根目录的"运行全部测试"要求。
只运行 `make test-payment`。

```

不要只写：

```
运行模块测试。

```

# 七、fallback 文件名有什么作用

部分团队已有自己的 AI 指导文件，例如：

```
TEAM_GUIDE.md
AI_INSTRUCTIONS.md
.agent-rules.md

```

不希望立即全部改名为：

```
AGENTS.md

```

Codex 支持通过：

```toml
project_doc_fallback_filenames

```

添加候选文件名。

例如：

```toml
project_doc_fallback_filenames = [
"TEAM_GUIDE.md",
".agents.md"
]

```

此时每个目录的检查顺序变成：

```
AGENTS.override.md
↓
AGENTS.md
↓
TEAM_GUIDE.md
↓
.agents.md

```

官方示例也说明，只有在标准 AGENTS 文件缺失时，Codex 才会尝试 fallback 名称。

## 1. fallback 不是额外加载

假设目录中同时存在：

```
AGENTS.md
TEAM_GUIDE.md

```

即使配置了 fallback，Codex 仍然只选择：

```
AGENTS.md

```

TEAM_GUIDE.md 不会被追加。

## 2. fallback 适合迁移场景

例如团队原来使用：

```
COPILOT_INSTRUCTIONS.md

```

可以先配置：

```toml
project_doc_fallback_filenames = [
"COPILOT_INSTRUCTIONS.md"
]

```

然后逐步迁移为标准：

```
AGENTS.md

```

## 3. fallback 不适合做多文档知识库

不应把：

```toml
project_doc_fallback_filenames = [
"ARCHITECTURE.md",
"API.md",
"DATABASE.md",
"DEPLOYMENT.md"
]

```

理解为会全部加载。

Fallback 的语义是：

```
替代文件名

```

而不是：

```
额外参考文档列表

```

详细资料更适合：

```
Skill references/
项目文档
MCP 知识库

```

# 八、32 KiB 限制如何影响 AGENTS 设计

Codex 会跳过空指导文件，并在累计读取内容达到：

```
project_doc_max_bytes

```

后停止加入更多项目指导。

默认值是：

```
32768 字节

```

即约：

```
32 KiB

```

该限制针对构建项目指令时读取的 AGENTS 内容。

需要注意：

```
32 KiB
≠
32000 个汉字

```

UTF-8 中文通常一个汉字占多个字节，所以中文可容纳字符数量会明显少于英文。

## 1. 限制是累计的

假设：

```
根目录 AGENTS.md：15 KiB
services/AGENTS.md：12 KiB
payment/AGENTS.md：10 KiB

```

总量：

```
37 KiB

```

超过默认限制。

Codex 会在达到上限后停止继续加入内容。

这意味着更靠近当前目录、原本更具体的规则，可能因为前面的文件过大而无法完整进入指令链。

这是一个非常重要的工程问题。

因为目录优先级逻辑本来是：

```
根目录通用
↓
子目录具体

```

但如果根目录塞入大量内容：

```
根目录占满预算
↓
子目录规则无法加载

```

就会破坏分层设计。

## 2. 根目录应该保持精简

根目录只应保存全仓库真正通用的规则，例如：

```
基础技术栈
统一构建命令
通用安全规则
代码提交流程
目录导航说明

```

不应放入：

```
每个模块的完整说明
所有 API 文档
数据库表结构
历史架构决策全文
几十个代码示例

```

## 3. 详细规则应向最近目录下沉

例如：

```
repo/AGENTS.md
→ 全局项目约定

backend/AGENTS.md
→ 后端约定

backend/payment/AGENTS.md
→ 支付模块约定

frontend/AGENTS.md
→ 前端约定

```

这既减少无关上下文，也提高规则的具体性。

OpenAI 也建议将指导放到最接近其适用目录的位置，并只记录真正反复出现、长期有效的规则。

## 4. 可以调大，但不能无限扩大

配置示例：

```toml
project_doc_max_bytes = 65536

```

可以将预算提高到约 64 KiB。

但扩大限制会带来：

```
初始上下文增加
Token 成本上升
模型注意力分散
规则冲突概率增加
Prompt Cache 更容易变化

```

所以更好的方案通常不是：

```
无限增加 project_doc_max_bytes

```

而是：

```
压缩通用规则
按目录拆分
把流程移入 Skill
把资料移入 references

```

# 九、AGENTS.md 应该写什么

AGENTS.md 最适合承载：

```
长期
稳定
高频
适用于目录范围内大多数任务

```

的规则。

## 1. 构建和测试命令

```markdown

## Validation

- Java 修改后运行 `./mvnw test`。
- 只修改文档时不需要运行测试。
- 修改数据库迁移时运行 `make verify-migrations`。

```

## 2. 目录导航

```markdown

## Repository layout

- API 定义位于 `api/`。
- 领域模型位于 `domain/`。
- 数据库迁移位于 `db/migrations/`。
- 不要优先阅读 `generated/`。

```

目录导航可以减少 Agent 无目的读取大量文件。

## 3. 架构边界

```markdown

## Architecture boundaries

- Controller 不直接访问 Repository。
- Domain 层不得依赖 Web 层。
- 跨模块访问必须通过公开 Service 接口。

```

## 4. 安全规则

```markdown

## Security

- 不要读取或提交 `.env`。
- 不要打印 Token、Cookie 或密码。
- 修改认证逻辑时必须补充安全测试。

```

## 5. 变更习惯

```markdown

## Change policy

- 优先进行最小修改。
- 不要顺便重构无关模块。
- 引入依赖前先说明理由。
- 改动公共接口时同步更新文档。

```

## 6. 团队反复反馈

如果代码审查中经常出现：

```
忘记添加测试
修改了生成文件
没有更新接口文档
跨层调用

```

就应该将它们沉淀进 AGENTS.md。

OpenAI 建议把反复出现的错误、重复的 PR 反馈和不必要的文件探索转化为 AGENTS 指导，让后续 Session 继承这些修正。

# 十、AGENTS.md 不应该写什么

## 1. 一次性任务

不适合：

```markdown
今天先修改 UserController。
这次不要运行测试。
处理 ISSUE-123。

```

这些应该写在当前用户 Prompt 中。

## 2. 复杂工作流全文

例如：

```
发布版本的 20 个执行步骤
数据库迁移的完整回滚流程
线上事故排查的详细 Runbook

```

这些更适合 Skill。

## 3. 大量参考资料

例如：

```
完整 API 文档
数据库字段字典
上百条业务规则
历史会议记录

```

适合：

```
references/
项目文档
知识库 MCP

```

## 4. 不可强制的安全幻想

例如：

```markdown
永远不要访问网络。
永远不要读取密钥。

```

这种指导有价值，但不能替代：

```
Permission
Sandbox
Network Policy
Deny Rule

```

AGENTS.md 是模型指令层，不是操作系统级安全控制。

## 5. 含糊规则

不推荐：

```
代码要优雅。
保持高质量。
适当测试。
尽量不要改太多。

```

推荐：

```
新增公共方法必须添加单元测试。
修改行为时优先复用现有测试夹具。
除非任务要求，不重命名无关类。

```

# 十一、AGENTS.md 与用户 Prompt 如何分工

可以用"长期规则"和"当前目标"区分。

AGENTS.md

回答：

```
在这个项目里，通常应该怎样工作？

```
用户 Prompt

回答：

```
这一次具体要完成什么？

```

例如：

AGENTS.md

```markdown
- 使用 Java 21。
- 修改后运行 Maven 测试。
- Controller 不直接访问 Repository。

```
当前 Prompt

```
为订单查询接口增加按状态过滤，
保持现有 API 兼容。

```

最终任务是：

```
项目规则
+
当前目标

```

而不是让用户每次重复全部项目要求。

## 1. 用户 Prompt 能否覆盖 AGENTS.md

在实际语义上，用户可以对当前任务提供更具体的要求。

例如：

```
AGENTS.md：
修改代码后运行完整测试。

用户 Prompt：
这次只修改 Markdown，不需要运行测试。

```

模型通常会按照当前任务的具体条件处理。

但如果用户要求与更高层系统或企业安全策略冲突，则不能通过普通 Prompt 绕过。

因此可以理解为：

```
系统与治理约束
>
项目长期指导
>
当前任务具体要求

但具体语义仍需要模型结合上下文判断

```

这不是简单的键值优先级。

# 十二、AGENTS.md 与 config.toml 如何分工

这是最容易混淆的边界。

AGENTS.md：行为指导

```
应该如何工作

```

例如：

```markdown
- 修改后运行测试。
- 优先复用现有组件。
- 不要访问 generated 目录。

```
config.toml：运行装配

```
Harness 允许如何运行

```

例如：

```toml
model = "gpt-5.6"
approval_policy = "on-request"
sandbox_mode = "workspace-write"

```

两者关系：

```
AGENTS.md
→ 告诉模型应当执行测试

config.toml
→ 决定运行测试是否需要审批
→ 决定命令能访问哪些目录和网络

```

例如：

```
AGENTS.md：
运行部署脚本。

config.toml：
sandbox_mode = read-only

```

Agent 即使知道应该运行部署脚本，也可能被运行时权限阻止。

因此：

```
AGENTS.md
→ 意图和方法

config.toml
→ 能力和边界

```

# 十三、AGENTS.md 与 Skill 如何分工

OpenAI 将 AGENTS 与 Skills 定义为互补能力。AGENTS 提供持久项目指导，而 Skill 提供可复用流程、脚本和参考资料，并采用渐进式加载。

## 1. AGENTS.md 适合持续规则

```
每次修改 Java 都运行测试
支付模块必须使用 BigDecimal
禁止直接修改生成代码

```

## 2. Skill 适合任务流程

例如：

```
数据库迁移
发布版本
修复 CI
生成架构报告
安全审查

```

一个数据库迁移 Skill 可以包含：

```
SKILL.md
scripts/
references/
templates/

```

## 3. 判断标准

可以问：

这段内容是否应该在每一个任务中持续存在？

如果答案是"是"，适合 AGENTS.md。

如果答案是：

```
只有执行某类任务时才需要

```

适合 Skill。

## 4. 错误示例

把完整发布流程写入根目录 AGENTS.md：

```
发布前检查版本
生成 Changelog
运行构建
上传 Artifact
创建 Tag
通知团队
……

```

即使用户只在修复一个小 Bug，这些内容也会进入项目指令预算。

更合理的是：

```
AGENTS.md：
发布操作必须使用 release Skill。

release Skill：
保存完整发布流程。

```

# 十四、AGENTS.md 与 Rules、Hooks 的分工

Codex 还有：

```
Rules
Hooks

```

它们与 AGENTS 指令层也不同。

AGENTS.md

```
用自然语言告诉 Agent 应遵守什么

```
Rules

```
在 Harness 层匹配和控制命令或行为

```
Hooks

```
在生命周期事件发生时运行检查或程序

```

例如禁止危险命令。

只用 AGENTS.md

```markdown
不要执行 rm -rf。

```

这只是模型指导。

使用 Rule 或 Hook

```
匹配危险 Bash
↓
强制 Ask 或 Deny

```

后者是运行时控制。

最好的模式是：

```
AGENTS.md
→ 告诉 Agent原因和正确做法

Rule / Hook
→ 强制阻止越界行为

```

# 十五、Subagent 是否继承 AGENTS.md

这是一个需要谨慎区分的问题。

Codex Custom Agent 的独立 TOML 文件会作为新生成 Session 的配置层。官方明确说明，如果 Custom Agent 没有覆盖某些配置，sandbox_mode、mcp_servers、skills.config 等会从父 Agent 继承。

但官方 Subagent 文档当前并没有用同样明确的字段表述直接承诺：

```
每个 Subagent 都会重新执行一遍完整 AGENTS.md 文件发现

```

因此，更稳妥的理解是：

```
主 Agent 已经基于项目环境和 AGENTS 指令工作
↓
创建 Subagent
↓
Subagent 获得父任务传递的上下文
并继承未被覆盖的 Session 配置

```

至于 AGENTS 指令是：

```
作为父 Session 指令继承
还是
在子 Session 中重新发现

```

从公开文档看，仍不适合做过度确定的内部实现断言。

## 1. 工程实践中不要依赖隐式继承

假设项目有关键规则：

```
不要修改数据库 Migration 历史文件

```

主 Agent 委托一个 Subagent：

```
分析数据库结构并提出修改方案

```

不应该只假设 Subagent 一定完整理解所有 AGENTS 规则。

更稳妥的委托是：

```
分析数据库结构。
遵循项目 AGENTS.md：
不要修改已有 Migration，
只提出新的迁移方案。

```

也就是说：

```
关键约束
→ 在 Subagent 任务中再次明确

```

## 2. Custom Agent 可以增加专属 developer_instructions

例如：

```toml
name = "security-reviewer"
description = "Review authentication and authorization code."

developer_instructions = """
Follow repository guidance.
Do not modify files.
Focus on privilege escalation, secret exposure, and authorization bypass.
Return findings with file paths and severity.
"""

```

这形成：

```
项目长期规则
+
角色专属规则
+
当前委托任务

```

## 3. 不要让 Custom Agent 与项目规则冲突

例如项目规则：

```
禁止修改生产配置。

```

Custom Agent 写：

```
必要时直接修改生产配置。

```

就形成自然语言冲突。

虽然上层安全与 Sandbox 可能阻止真正越权，但行为会变得不稳定。

因此 Agent Definition 应该：

```
细化项目规则
而不是推翻项目规则

```

# 十六、CLI、IDE 与 App 中的 AGENTS 行为

Codex CLI、IDE 和 App 共享 Codex Harness 的多项配置和项目能力，但它们的工作目录和执行环境可能不同。

因此 AGENTS 发现结果取决于：

```
当前项目
当前工作目录
项目根识别
本地还是 Worktree
是否为 Cloud Environment

```

## 1. CLI

CLI 中最直观：

```bash
cd services/payment
codex

```

当前工作目录是：

```
services/payment

```

因此发现链通常从项目根到该目录。

还可以通过：

```bash
codex --cd services/payment

```

显式指定工作目录。官方 AGENTS 指南也使用 --cd 验证目录级指导加载来源。

## 2. IDE

IDE 中通常以当前打开的 Workspace 或 Repository 作为项目环境。

但需要关注：

```
IDE 打开的根目录
当前文件所属目录
Codex Session 的实际 cwd
多根 Workspace

```

如果 IDE Workspace 打开的不是实际 Git 根，AGENTS 发现链可能与 CLI 中不同。

## 3. Desktop App 与本地 Worktree

Codex App 可以为并行 Agent 创建独立 Worktree。

Worktree 中跟踪在 Git 中的 AGENTS.md 会自然存在。

对于被 Git 忽略的本地：

```
AGENTS.override.md

```

Codex 管理的本地 Worktree 会自动复制该文件，不需要把它额外加入 .worktreeinclude。该行为适用于本地 Codex 管理 Worktree，不适用于远程 Worktree 或用户自行创建的普通 Git Worktree。

这说明 Override 被视为重要的本地工作指导。

## 4. Cloud

Codex Cloud 在隔离环境中加载 Repository，并根据所选环境执行任务。

提交到仓库的：

```
AGENTS.md
嵌套 AGENTS.md

```

可以随 Repository 进入 Cloud 环境。

但本地用户目录中的：

```
~/.codex/AGENTS.md
本地未提交的 AGENTS.override.md

```

不会天然等同于 Cloud 环境中的全局配置。

因此，如果希望团队在：

```
CLI
IDE
App
Cloud

```

获得一致规则，关键指导应该提交到 Repository 中，而不是只保存在本地全局文件里。

# 十七、一个完整的多层 AGENTS 案例

假设项目结构如下：

```
commerce-platform/
├── AGENTS.md
│
├── backend/
│ ├── AGENTS.md
│ │
│ ├── order/
│ │ ├── AGENTS.md
│ │ └── src/
│ │
│ └── payment/
│ ├── AGENTS.override.md
│ └── src/
│
└── frontend/
├── AGENTS.md
└── src/

```

## 1. 根目录

```markdown

# Repository rules

- 优先进行最小范围修改。
- 不要修改 generated 目录。
- 新增公共行为必须补充测试。
- 不要提交 Secret。

```

## 2. Backend

```markdown

# Backend rules

- 使用 Java 21。
- 使用 Maven Wrapper。
- Controller 不直接访问 Repository。
- 修改后运行相关模块测试。

```

## 3. Order

```markdown

# Order service rules

- 状态变化必须经过 OrderDomainService。
- 不要直接更新订单状态字段。
- 修改状态机时补充迁移路径测试。

```

## 4. Payment Override

```markdown

# Payment local override

- 当前只进行只读安全审计。
- 不修改代码。
- 不运行会写入数据库的测试。
- 优先检查金额精度、重复支付和权限绕过。

```

## 5. 在不同目录启动的结果
在 Repository 根启动

```
全局 AGENTS
+
Repository AGENTS

```
在 backend/order 启动

```
全局 AGENTS
+
Repository AGENTS
+
Backend AGENTS
+
Order AGENTS

```
在 backend/payment 启动

```
全局 AGENTS
+
Repository AGENTS
+
Backend AGENTS
+
Payment AGENTS.override

```

其中 Payment 目录中的普通 AGENTS.md 如果存在，也会因为 Override 而被忽略。

# 十八、如何调试 AGENTS.md 是否生效

最直接的方式，是让 Codex输出当前加载的指导来源。

例如：

```bash
codex --ask-for-approval never \
"列出当前加载的 AGENTS 指令来源，并总结每一层规则。"

```

也可以指定目录：

```bash
codex --cd services/payment \
--ask-for-approval never \
"列出当前 Instruction Chain 的来源顺序。"

```

官方指南也建议通过类似命令验证全局、根目录和局部 Override 的加载顺序。

## 1. 常见问题：根目录规则没加载

检查：

```
是否从正确目录启动
项目根是否识别正确
project_root_markers 是否配置不当
AGENTS 文件是否为空
是否达到大小限制

```

## 2. 常见问题：AGENTS.md 被忽略

检查同级是否存在：

```
AGENTS.override.md

```

如果存在非空 Override，普通文件不会加载。

## 3. 常见问题：fallback 没生效

检查：

```
project_doc_fallback_filenames 是否配置
同目录是否已有 AGENTS.md
文件名大小写是否正确

```

Fallback 只在标准文件缺失时使用。

## 4. 常见问题：子目录规则没生效

检查：

```
Codex 的实际 cwd
子目录是否位于项目根到 cwd 的路径上
前面内容是否已达到 project_doc_max_bytes

```

## 5. 常见问题：修改后当前 Session 没变化

AGENTS 指令链通常在运行启动时构建一次。修改文件后，当前 Session 不一定重新发现，应重新启动相应 Session 进行验证。

# 十九、AGENTS.md 的设计原则

## 1. 规则靠近适用目录

```
全仓库规则
→ 根目录

后端规则
→ backend/

支付规则
→ payment/

```

## 2. 根目录保持最小

根目录只写真正通用的内容，避免消耗全部字节预算。

## 3. 使用可执行、可验证的表达

不写：

```
保证代码质量。

```

而写：

```
修改 Java 代码后运行 `./mvnw test`。

```

## 4. 避免无意义重复

如果根目录已经声明：

```
禁止提交 Secret

```

每个子模块不必重复，除非有更具体规则。

## 5. 明确替代关系

下层规则与上层不同，应写：

```
本目录使用 `make test-payment` 替代根目录的 `./mvnw test`。

```

## 6. 将流程移入 Skill

凡是包含：

```
多个阶段
条件判断
模板
脚本
参考资料

```

的内容，优先拆成 Skill。

## 7. 将强制限制交给运行时

涉及：

```
文件禁止访问
网络禁止访问
危险命令
权限边界

```

不能只依赖 AGENTS，应配合 Permission、Rule、Hook 和 Sandbox。

# 二十、从 AGENTS.md 看 Codex 的设计思想

## 1. 指令跟随代码分发

项目规则可以提交进 Repository，成为工程资产。

## 2. 目录结构就是作用域结构

Codex 不需要复杂的 Scope 配置，而是直接利用：

```
项目根
子目录
当前目录

```

形成指令作用域。

## 3. 继承与局部细化并存

```
根目录
→ 通用规则

子目录
→ 领域规则

当前目录
→ 任务最近规则

```

## 4. Override 提供本地替换能力

不需要删除或修改基础文件，就可以临时改变当前目录行为。

## 5. 指令与能力分离

```
AGENTS
→ 指导

Skill
→ 工作流

config
→ 运行配置

Permission
→ 强制边界

```

这种职责拆分避免把所有内容堆进一个 Prompt 文件。

# 二十一、这套机制的优势

## 1. 简单

只需要 Markdown 文件，不需要复杂 Schema。

## 2. Git 友好

项目规则可审查、可版本管理、可跟随分支变化。

## 3. 适合 Monorepo

不同目录可以维护自己的局部规则。

## 4. 支持个人与团队叠加

```
全局个人偏好
+
项目团队规则
+
模块局部规则

```

## 5. 不强依赖特定 IDE

只要使用同一 Repository 和工作目录，多个 Codex Surface 都能利用项目指导。

# 二十二、这套机制的局限

## 1. 覆盖依赖自然语言理解

不是确定性的字段级 Merge。

## 2. 冲突难以静态检查

两个目录的规则互相矛盾时，没有统一 Schema 自动报错。

## 3. 大文件会挤占上下文

根目录内容过多可能导致局部规则无法完整加载。

## 4. 启动时构建，不一定实时刷新

修改后通常需要新 Session 验证。

## 5. Subagent 继承细节不够完全透明

关键约束仍应在委托任务中再次明确。

## 6. 不能代替权限控制

模型指导不是安全 Sandbox。

## 7. 不适合复杂流程

复杂工作流应该进入 Skill，而不是无限扩张 AGENTS。

# 二十三、对自研 Harness 的启发

如果设计自研 Harness，可以保留 Codex 的目录式指导模型：

```
Global Instructions
↓
Project Instructions
↓
Module Instructions
↓
Task Instructions

```

但可以增加结构化元数据。

例如：

```yaml
scope: module
appliesTo:
- "src/main/java/**"

priority: 30

rules:
```

总结

AGENTS.md 是 Codex 项目指导体系的核心入口。

它并不是一个单独文件，而是一条分层指令链。

完整发现过程是：

```
Codex 启动
↓
读取全局 AGENTS.override.md 或 AGENTS.md
↓
识别项目根
↓
从项目根走向当前工作目录
↓
每个目录选择一个指导文件
↓
按照根到当前目录的顺序拼接
↓
形成当前 Session 的 Instruction Chain

```

全局层的选择规则是：

```
AGENTS.override.md
>
AGENTS.md

```

项目每个目录中的选择规则是：

```
AGENTS.override.md
>
AGENTS.md
>
project_doc_fallback_filenames

```

每个目录最多选择一个文件。多个目录的内容则从项目根到当前目录依次拼接，因此越靠近当前目录的指导越具体，并在组合 Prompt 中出现得更晚。

项目根通常是 Git 根，也可以通过：

```toml
project_root_markers

```

自定义。如果找不到项目根，Codex 只检查当前工作目录。

整个项目指导链受到：

```toml
project_doc_max_bytes

```

限制，默认约为：

```
32 KiB

```

因此根目录 AGENTS 应保持精简，具体规则应尽量下沉到对应模块目录，复杂流程则应迁移到 Skill。

几种能力的边界可以概括为：

```
AGENTS.md
→ 每次任务都应遵循的长期项目规则

用户 Prompt
→ 当前任务目标

Skill
→ 某类任务的完整可复用流程

config.toml
→ 模型、MCP、Agent、Approval 和 Sandbox 配置

Rules / Hooks
→ 运行时强制检查和事件处理

```

从架构角度看，Codex 的指导模型可以抽象成：

```
Global Guidance
+
Repository Guidance
+
Directory Guidance
+
Current Task

```

也就是说：

AGENTS.md 不是让项目拥有一个更长的 Prompt，而是让项目目录本身变成一套可继承、可覆盖、可版本管理的 Agent 指令作用域。
